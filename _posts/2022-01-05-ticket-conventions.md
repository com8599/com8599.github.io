개발이 느려지는 원인을 코드에서만 찾으면 절반을 놓친다. 작업은 티켓에서 시작하고, 티켓이 모호하면 개발자는 질문하고 기다리거나 추측해서 만든 뒤 다시 고친다. 둘 다 개발 시간이 아니라 **대기와 재작업**으로 쓰이는 시간이다. 티켓 작성 규칙은 문서 형식을 맞추는 일이 아니라, 이 두 비용을 작업이 시작되기 전에 줄이는 장치다.

## 모호한 티켓이 비용을 만드는 경로

"로그인 개선" 같은 한 줄 티켓을 받았을 때 생기는 일은 대체로 세 가지다.

| 상황 | 결과 | 비용 |
|---|---|---|
| 작성자에게 질문한다 | 답이 올 때까지 작업이 멈춘다 | 대기 시간 |
| 추측해서 구현한다 | 리뷰나 QA에서 "그게 아니다"가 나온다 | 재작업 |
| 범위를 넓게 잡는다 | 필요 없는 것까지 만든다 | 과잉 구현 |

질문은 비동기로 오가기 때문에 한 번의 왕복에 반나절이 걸리기도 한다. 추측은 더 비싸다. 잘못된 이해는 구현이 끝난 뒤, 즉 비용이 가장 커진 시점에 드러난다. 결함은 늦게 발견될수록 고치는 비용이 커진다는 흔히 인용되는 경험칙은 요구사항 단계의 모호함에도 적용된다. 정확한 배수는 환경마다 다르지만, 구현과 리뷰를 다시 거쳐야 한다는 점만으로도 비용은 분명히 늘어난다.

공통 원인은 **완료 조건이 없다는 것**이다. 무엇을 만들면 끝인지 정해지지 않은 작업은 시작할 수는 있어도 끝낼 수는 없다.

## 이슈 유형을 먼저 나눈다

티켓에 무엇을 써야 하는지는 작업의 성격에 따라 다르다. 버그에는 재현 절차가 필요하고, 기능 요청에는 사용자 관점의 목표가 필요하다. 모든 티켓에 같은 양식을 강요하면 필요 없는 칸은 비워지고 필요한 칸은 빠진다.

| 유형 | 목적 | 필수 정보 |
|---|---|---|
| 기능(Story) | 사용자에게 새 가치 제공 | 배경, 목표, 인수 조건 |
| 버그(Bug) | 기대와 다른 동작 수정 | 재현 절차, 기대 결과, 실제 결과, 환경 |
| 작업(Task) | 기술 부채, 설정, 운영 작업 | 목적, 완료 기준 |
| 조사(Spike) | 불확실성 해소 | 답할 질문, 시간 상한 |

조사 티켓에 시간 상한을 두는 이유는 결과물이 코드가 아니라 **결정에 필요한 정보**이기 때문이다. 상한이 없으면 조사는 끝나지 않는다.

## 인수 조건(Acceptance Criteria)

인수 조건은 "이 조건을 만족하면 요구가 충족된 것으로 본다"는 검증 가능한 문장이다. 좋은 인수 조건은 다음 성질을 가진다.

- **관찰 가능하다**: "빠르게 응답한다"가 아니라 "p95 응답이 300ms 이하다".
- **결과를 기술한다**: 구현 방법이 아니라 동작을 적는다.
- **경계를 포함한다**: 정상 경로뿐 아니라 실패, 빈 값, 권한 없음 같은 경우를 적는다.

인수 조건은 그대로 테스트 케이스와 리뷰 체크리스트가 된다. 작성자와 구현자와 검증자가 같은 문장을 보고 판단하기 때문에 "그게 아니다"가 나올 여지가 줄어든다.

## 준비 완료 정의와 완료 정의

티켓이 작업 흐름에 들어가고 나가는 두 지점에 기준을 둔다.

**완료 정의(Definition of Done)** 는 스크럼 가이드(Scrum Guide)에 정의된 개념이다. 2020년판 가이드는 이를 제품에 요구되는 품질 기준을 충족했을 때 증분(Increment)의 상태에 대한 공식적인 설명으로 정의하고, 증분에 대한 약속(commitment)으로 둔다. 백로그 항목이 완료 정의를 충족하는 순간 증분이 만들어지며, 충족하지 못한 항목은 릴리스하거나 스프린트 리뷰에서 보여줄 수도 없고 제품 백로그로 돌아간다.

완료 정의는 개별 티켓의 인수 조건과 다르다. 인수 조건이 "이 기능이 무엇을 해야 하는가"라면, 완료 정의는 "모든 작업이 공통으로 갖춰야 할 품질 상태"다.

- 코드 리뷰 승인
- 단위 테스트 추가, CI 통과
- 스테이징 배포 후 인수 조건 확인
- API 변경 시 문서 갱신

**준비 완료 정의(Definition of Ready)** 는 반대편, 즉 작업을 시작해도 되는 상태의 기준이다. 이것은 스크럼 가이드에 있는 개념이 **아니다**. 가이드는 정제(refinement)를 거쳐 한 스프린트 안에 끝낼 수 있는 항목을 스프린트 계획에서 선택할 준비가 된 것으로 본다고만 쓸 뿐, 별도의 체크리스트를 정의하지 않는다. 준비 완료 정의는 현장에서 널리 쓰이는 보조 관행이다.

준비 완료 정의는 흔히 이런 항목으로 구성한다.

- 이슈 유형별 필수 항목이 채워져 있다
- 인수 조건이 하나 이상 있다
- 외부 의존성(다른 팀, 디자인, API 스펙)이 해소됐거나 명시돼 있다
- 담당 개발자가 크기를 추정할 수 있다

주의할 점은 준비 완료 정의가 관문이 되어 작업을 막는 방향으로 변질되기 쉽다는 것이다. 모든 불확실성을 사전에 제거하려 하면 티켓이 백로그에서 늙어 간다. 기준은 "시작하면 질문 때문에 멈추지 않을 정도"로 두고, 남은 불확실성은 조사 티켓으로 분리하는 편이 낫다.

## 우선순위와 심각도를 분리한다

버그 티켓에서 자주 섞이는 두 축이 있다.

| | 심각도(Severity) | 우선순위(Priority) |
|---|---|---|
| 질문 | 결함이 시스템에 주는 영향이 얼마나 큰가 | 언제 처리해야 하는가 |
| 판단 주체 | 주로 보고자, QA, 개발자 | 주로 제품 책임자, 리드 |
| 성격 | 기술적 영향 | 비즈니스 중요도와 긴급도 |

ISTQB 용어집도 심각도를 결함이 컴포넌트나 시스템의 개발·운영에 주는 영향의 정도로, 우선순위를 비즈니스 관점의 중요도로 구분한다.

두 축이 하나의 필드로 합쳐지면 판단이 왜곡된다. 거의 쓰이지 않는 관리자 화면이 죽는 결함은 심각도는 높지만 우선순위는 낮을 수 있다. 결제 화면의 오탈자는 심각도는 낮지만 당장 고쳐야 할 수 있다. 필드를 나누면 보고자는 사실(영향)만 기록하고, 순서 결정은 그 정보를 바탕으로 따로 내릴 수 있다.

## 티켓 템플릿 예시

버그 유형 템플릿의 예다.

```markdown
## 요약
결제 완료 후 주문 내역 화면에 금액이 0원으로 표시된다.

## 환경
- 앱 버전: 3.4.1 (Android)
- 서버: production
- 발생 시각: 2022-01-04 14:20 KST 전후

## 재현 절차
1. 쿠폰을 적용해 상품을 결제한다.
2. 마이페이지 > 주문 내역으로 이동한다.

## 기대 결과
쿠폰 할인 후 실제 결제 금액이 표시된다.

## 실제 결과
금액이 0원으로 표시된다. 쿠폰 없이 결제하면 정상.

## 심각도 / 우선순위
- 심각도: 중간 (결제 자체는 정상, 표시 오류)
- 우선순위: 보고 후 결정

## 인수 조건
- 쿠폰 적용 주문의 금액이 결제 금액과 일치한다.
- 쿠폰 미적용 주문은 기존과 동일하게 표시된다.
- 기존 주문 데이터에도 올바른 금액이 표시된다.
```

기능 유형은 "배경(왜 필요한가) / 목표(사용자가 무엇을 할 수 있게 되는가) / 범위 밖(이번에 하지 않는 것) / 인수 조건"으로 구성한다. 특히 **범위 밖** 항목은 과잉 구현과 범위 확장을 막는 데 효과가 크다.

## 규칙이 있어야 흐름을 측정할 수 있다

작성 규칙의 두 번째 효과는 측정이다. 칸반 가이드(Kanban Guide)는 흐름 지표로 진행 중 작업(WIP), 처리량(Throughput), 작업 항목 나이(Work Item Age), 사이클 타임(Cycle Time)을 든다. 사이클 타임은 작업 항목이 시작된 시점부터 끝난 시점까지의 경과 시간이다.

이 지표들은 "시작"과 "끝"이 일관되게 정의돼 있어야 의미가 있다. 칸반 가이드가 워크플로 정의(Definition of Workflow)에 시작점과 종료점, 상태, 상태 간 이동에 대한 명시적 정책을 포함하라고 하는 것도 같은 이유다.

| 규칙이 없을 때 | 규칙이 있을 때 |
|---|---|
| 어떤 사람은 착수 시, 어떤 사람은 PR 생성 시 "진행 중"으로 옮긴다 | "진행 중" 진입 조건이 정해져 있다 |
| 리뷰 대기와 개발 중이 한 상태에 섞인다 | 대기 상태가 별도로 보인다 |
| 완료 기준이 사람마다 다르다 | 완료 정의를 충족해야 "완료"로 옮긴다 |
| 버그와 기능이 섞여 평균이 무의미하다 | 이슈 유형별로 분포를 비교할 수 있다 |

측정이 가능해지면 개선 대상을 감이 아니라 데이터로 고를 수 있다. 예를 들어 사이클 타임의 대부분이 "리뷰 대기"에 있다면 문제는 티켓 작성이 아니라 리뷰 용량이다. 반대로 "진행 중"에서 "보류"로 되돌아가는 비율이 높다면 준비 완료 정의가 부족하다는 신호다.

## 정리

1. 모호한 티켓의 비용은 질문 대기와 재작업으로 나타나며, 구현이 끝난 뒤 드러날수록 커진다.
2. 이슈 유형별로 필수 정보를 다르게 정하고, 모든 작업 티켓에 검증 가능한 인수 조건을 둔다.
3. 완료 정의는 스크럼 가이드의 공식 개념이고, 준비 완료 정의는 가이드 밖의 보조 관행이다. 후자는 관문이 아니라 멈춤 방지 기준으로 쓴다.
4. 심각도와 우선순위를 분리해 사실 기록과 순서 결정을 나눈다.
5. 상태 전이 규칙이 일관돼야 사이클 타임 같은 흐름 지표가 의미를 갖고, 병목을 데이터로 찾을 수 있다.
