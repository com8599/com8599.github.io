작업이 늦게 끝나는 이유는 대개 작업 자체가 오래 걸려서가 아니다. 아무도 손대지 않은 채 기다리는 시간이 길어서다. 담당자가 없는 티켓, 담당자는 있지만 아무도 상태를 보지 않는 티켓은 백로그 안에서 조용히 늙어 간다. 이 글은 그 대기 시간을 줄이는 두 장치, 배정 규칙과 에스컬레이션 규칙을 다룬다.

## 리드 타임은 대부분 대기 시간이다

요청이 들어온 시점부터 완료까지를 리드 타임(Lead Time)이라고 한다. 리드 타임은 실제로 누군가 작업하는 시간과 기다리는 시간으로 나뉜다. 이 비율을 나타내는 지표가 흐름 효율(Flow Efficiency)이다.

Kanban University는 흐름 효율을 활성 작업 시간(대기 제외)을 전체 리드 타임(작업 + 대기)으로 나누고 100%를 곱한 값으로 설명한다. 리드 타임이 10일인데 실제 작업이 2일이었다면 흐름 효율은 20%다. 칸반 관련 자료들은 대부분의 시스템에서 대기 상태에 머무는 시간이 실제 작업 시간보다 길다고 지적한다. 분모를 리드 타임 대신 사이클 타임으로 잡는 경우도 있으므로, 팀 간 수치를 비교할 때는 기준을 먼저 맞춰야 한다.

여기서 중요한 결론은 이렇다. 흐름 효율이 낮은 시스템에서는 **작업을 빨리 하는 것보다 기다리는 시간을 줄이는 것**이 리드 타임에 훨씬 큰 영향을 준다. 작업 시간 2일을 1일로 줄이면 리드 타임은 10%만 줄지만, 대기 8일을 4일로 줄이면 40%가 준다.

## 대기는 어디서 생기는가

티켓이 기다리는 지점은 대체로 정해져 있다.

| 대기 지점 | 원인 |
|---|---|
| 신규 → 배정 | 누가 맡을지 정해지지 않았다 |
| 배정 → 착수 | 담당자의 다른 작업이 많다 (WIP 과다) |
| 진행 중 → 리뷰 | 리뷰어가 정해지지 않았거나 바쁘다 |
| 질문 → 답변 | 작성자가 답할 책임을 인지하지 못한다 |
| 보류 | 보류 사유와 해제 조건이 없다 |

이 중 가장 다루기 쉬운 것은 첫 번째, **담당자 공백**이다. 담당자가 없는 작업은 모두의 일이면서 누구의 일도 아니다. "누군가 보겠지"라는 가정이 겹치면 실제로는 아무도 보지 않는다.

## 작업 항목 나이(Work Item Age)

칸반 가이드(Kanban Guide)는 필수 흐름 지표 중 하나로 작업 항목 나이를 든다. 작업이 시작된 시점부터 현재까지의 경과 시간이다. 사이클 타임이 끝난 작업에 대한 사후 지표라면, 작업 항목 나이는 **아직 끝나지 않은 작업**에 대한 선행 지표다.

가이드는 서비스 수준 기대치(Service Level Expectation, SLE)를 "작업 항목이 시작부터 완료까지 흐르는 데 걸릴 것으로 예상되는 시간"으로 정의하고, 경과 시간과 그에 대한 확률의 두 부분으로 표현하게 한다. 예를 들어 "버그의 85%는 시작 후 5일 안에 끝난다" 같은 형태다. 그리고 작업 항목이 불필요하게 늙지 않도록 SLE를 기준으로 관리하라고 한다.

이 개념을 실무 규칙으로 옮기면 다음과 같다.

- 과거 사이클 타임 분포에서 유형별 기준을 정한다.
- 기준의 일정 비율(예: 50%, 100%)에 도달한 티켓을 표시한다.
- 기준을 넘긴 티켓은 일일 회의나 정기 점검에서 우선 다룬다.

칸반 가이드의 작업 항목 나이는 "시작된" 작업에 대한 지표다. 아직 시작되지 않은 신규 티켓의 대기는 별도로, 생성 후 배정까지의 시간 같은 지표로 본다.

## 배정 방식: 푸시와 풀

티켓을 사람에게 연결하는 방식은 크게 두 가지다.

| 방식 | 동작 | 장점 | 단점 |
|---|---|---|---|
| 규칙 기반 배정(Push) | 규칙에 따라 담당자를 자동 지정 | 담당자 공백이 없다 | 담당자의 현재 부하를 무시할 수 있다 |
| 풀(Pull) | 여유가 생긴 사람이 가져간다 | WIP가 자연스럽게 제한된다 | 아무도 가져가지 않는 티켓이 생긴다 |

규칙 기반 배정에는 흔히 두 가지 전략을 쓴다.

- **컴포넌트 담당자(Component Owner)**: 결제, 인증, 알림처럼 영역별로 기본 담당자를 둔다. 맥락을 아는 사람이 받으므로 처리가 빠르다. 대신 담당자 부재 시 대체자가 필요하다.
- **라운드 로빈(Round-robin)**: 순번대로 돌아가며 배정한다. 부하가 고르게 퍼지지만 맥락 전환 비용이 생긴다.

칸반 가이드는 WIP 통제가 용량이 있을 때만 새 작업을 시작하는 풀 시스템을 만들어야 한다고 본다. 이 원칙과 자동 배정은 충돌하지 않는다. 자동 배정을 **"착수 지시"가 아니라 "1차 확인 책임자 지정"**으로 정의하면 된다. 배정받은 사람은 즉시 작업할 의무가 아니라, 정해진 시간 안에 티켓을 보고 받을지, 넘길지, 보류할지를 결정할 의무를 진다. 담당자 공백은 없애면서 착수 시점은 여전히 용량에 따라 결정된다.

## 에스컬레이션(Escalation) 규칙

배정만으로는 부족하다. 배정된 사람이 휴가 중이거나 다른 일에 묶여 있으면 티켓은 여전히 멈춘다. 에스컬레이션은 **정해진 시간 안에 상태가 바뀌지 않으면 더 넓은 범위에 알리는 규칙**이다.

좋은 에스컬레이션 규칙의 조건은 다음과 같다.

- **기준이 시간과 상태로 정의된다**: "오래된 티켓"이 아니라 "우선순위 높음, 생성 후 4시간 동안 미확인".
- **단계가 있다**: 담당자 → 팀 리드 → 팀 채널 순으로 범위를 넓힌다.
- **대상 행동이 명확하다**: 알림을 받은 사람이 무엇을 해야 하는지(재배정, 우선순위 조정)가 정해져 있다.
- **해제 조건이 있다**: 상태가 바뀌면 다음 단계 알림은 취소된다.

아래는 특정 도구의 문법이 아니라, 이런 규칙을 구조화해 적어 본 **일반적인 규칙 정의 예시**다.

```yaml
# 일반 규칙 정의 예시 (특정 도구 문법 아님)
assignment:
  - match: { type: bug, component: payment }
    assign_to: component_owner
    fallback: round_robin(backend_team)
  - match: { type: bug }
    assign_to: round_robin(backend_team)
  - match: { type: story }
    assign_to: none            # 계획 회의에서 풀 방식으로 가져감

escalation:
  - match: { priority: highest, status: new }
    steps:
      - after: 1h
        notify: assignee
      - after: 4h
        notify: team_lead
      - after: 1d
        notify: team_channel
    cancel_when: status != new

  - match: { status: in_progress }
    when: age > sle_for(type)   # 유형별 SLE 초과
    notify: assignee
    repeat: daily_digest        # 개별 알림 대신 하루 한 번 묶어서

  - match: { status: on_hold }
    require_fields: [hold_reason, resume_condition]
    when: unchanged_for > 7d
    notify: reporter
```

규칙의 핵심은 우선순위에 따라 시간 기준을 다르게 둔다는 것이다. 모든 티켓에 같은 기준을 적용하면 긴급한 티켓은 너무 늦게, 사소한 티켓은 너무 자주 알림이 간다.

## 알림 과잉을 피한다

에스컬레이션이 실패하는 가장 흔한 이유는 규칙이 없어서가 아니라 알림이 너무 많아서다. 매번 무시해도 괜찮았던 알림은 결국 모든 알림을 무시하게 만든다.

| 증상 | 대응 |
|---|---|
| 티켓 하나에 상태 변경마다 알림 | 의미 있는 전이(배정, 차단, 기준 초과)만 알린다 |
| 낮은 우선순위도 즉시 개인 알림 | 일일 요약으로 묶는다 |
| 모든 팀원에게 동일한 알림 | 담당자와 다음 단계 책임자에게만 보낸다 |
| 알림을 받아도 할 일이 없다 | 행동이 정해지지 않은 알림은 제거한다 |

규칙을 추가할 때는 그 알림을 받은 사람이 **무엇을 할 수 있는지** 먼저 적어 본다. 답이 없으면 그 알림은 대시보드나 요약으로 충분하다. 규칙을 운영한 뒤에는 알림 수 대비 실제 조치(재배정, 상태 변경) 비율을 보고 기준을 조정한다.

## 무엇으로 효과를 보는가

배정과 에스컬레이션의 효과는 다음 지표로 확인한다.

- 생성부터 첫 배정까지의 시간
- 생성부터 첫 상태 변경(확인)까지의 시간
- SLE를 넘긴 진행 중 티켓의 수와 비율
- 흐름 효율 (상태별 체류 시간에서 대기 상태 비중)

평균만 보면 오래 방치된 소수의 티켓이 가려진다. 백분위(p50, p85)와 기준 초과 건수를 함께 본다.

## 정리

1. 흐름 효율이 낮은 시스템에서는 작업 속도보다 대기 시간이 리드 타임을 좌우한다.
2. 담당자 공백은 가장 흔하고 가장 고치기 쉬운 대기 원인이다.
3. 작업 항목 나이와 SLE로 끝나지 않은 작업의 위험을 미리 본다.
4. 자동 배정은 착수 지시가 아니라 1차 확인 책임자 지정으로 정의하면 풀 원칙과 공존할 수 있다.
5. 에스컬레이션은 시간·상태 기준, 단계, 해제 조건을 갖추고, 행동으로 이어지지 않는 알림은 줄인다.
