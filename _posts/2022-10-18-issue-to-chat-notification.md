이슈가 등록된 뒤 해결되기까지의 시간은 "고치는 데 걸린 시간"만으로 이뤄지지 않는다. 그 앞에 **누군가 이슈의 존재를 알아채기까지의 시간**이 있다. 이 구간은 코드 품질이나 개발자 역량과 무관하게, 정보가 사람에게 전달되는 구조에 의해 결정된다. 이슈 트래커와 메신저를 연동하는 일은 이 구간을 줄이는 구조 변경이다.

## 대응 시간을 나누어 본다

장애 대응 분야에서는 대응 과정을 여러 구간으로 나누어 측정한다. Atlassian의 인시던트 관리 문서는 대표적인 지표를 이렇게 설명한다.

| 지표 | 의미 |
|---|---|
| MTTA(Mean Time To Acknowledge) | 인시던트를 인지하고 대응을 시작하기까지 걸리는 평균 시간 |
| MTTR(Mean Time To Repair) | 시스템을 수리하는 데 걸리는 평균 시간. 수리와 테스트 시간을 포함 |
| MTTR(Mean Time To Recovery) | 장애 발생부터 완전히 정상화될 때까지의 평균 시간 |
| MTTR(Mean Time To Respond) | 장애 알림을 받은 시점부터 복구까지의 평균 시간. 알림 시스템의 지연은 제외 |
| MTTR(Mean Time To Resolve) | 탐지·진단·수리에 더해 재발 방지까지 포함해 완전히 해결하는 데 걸리는 평균 시간 |

같은 약어 MTTR이 여러 의미로 쓰이므로, 지표를 도입할 때는 어떤 정의인지 먼저 정해야 한다.

일반 이슈 트래커의 업무 이슈에도 같은 분해가 적용된다. 생성부터 해결까지의 시간은 대략 다음 구간으로 나뉜다.

1. **인지**: 이슈가 등록된 뒤 담당자가 그 존재를 알게 되기까지
2. **분류(Triage)**: 심각도와 담당 영역을 판단하고 배정하기까지
3. **처리**: 원인을 찾고 수정하기까지
4. **확인**: 수정이 배포되고 보고자가 확인하기까지

이 중 1번은 순수한 대기 시간이다. 그리고 많은 팀에서 이 구간이 생각보다 길다.

## 풀(Pull) 방식: 확인 주기가 대응 시간의 하한이 된다

알림 연동이 없는 환경에서 사람들은 트래커를 **주기적으로 직접 열어** 새 이슈를 확인한다. 이것이 풀 방식이다. 기술적으로는 폴링(polling)과 같은 구조다.

폴링에서 이벤트 감지 지연은 폴링 주기에 묶인다. 주기가 T일 때 이벤트가 임의 시점에 발생한다면 감지까지 최대 T, 평균적으로 약 T/2가 걸린다. 사람의 확인 주기도 마찬가지다.

| 확인 습관 | 인지까지 최대 지연 |
|---|---|
| 매일 아침 확인 | 약 1일 |
| 주간 회의 때 확인 | 약 1주 |
| 생각날 때 확인 | 상한 없음 |

여기서 중요한 점은 이 지연이 **처리 속도를 아무리 높여도 줄지 않는다**는 것이다. 처리를 1시간 만에 끝내는 팀이라도 이슈를 주간 회의에서 처음 본다면 대응 시간은 일주일 단위가 된다. 게다가 사람의 확인은 업무가 바쁠수록 뒤로 밀린다. 즉 부하가 높아 이슈가 많이 생기는 시기에 오히려 확인 주기가 길어진다.

## 푸시(Push) 방식: 이벤트가 사람을 찾아간다

푸시 방식에서는 이슈가 생성되거나 상태가 바뀌는 **이벤트가 발생한 시점에** 알림이 전달된다. 이를 구현하는 일반적인 수단이 웹훅(Webhook)이다.

웹훅은 특정 이벤트가 발생했을 때 미리 등록된 URL로 HTTP 요청을 보내는 콜백 방식이다. GitHub 문서도 웹훅을 이벤트가 발생할 때마다 외부 웹 서버로 알림을 전달하는 방법으로 설명하며, API를 주기적으로 호출하는 폴링과 달리 데이터가 발생하는 즉시 받을 수 있고 자원도 덜 든다고 비교한다.

| | 풀(폴링) | 푸시(웹훅) |
|---|---|---|
| 감지 지연 | 확인 주기에 비례 | 이벤트 발생 직후 |
| 사람의 부담 | 주기적으로 기억해서 확인 | 알림이 오면 판단 |
| 바쁠 때 | 확인이 밀린다 | 알림은 계속 도착한다 |
| 위험 | 놓침 | 알림 과잉 |

이슈 트래커가 웹훅을 직접 지원하지 않더라도 플러그인이나 중계 서버를 두면 같은 구조를 만들 수 있다. 중계 서버는 트래커 이벤트를 받아 메신저의 수신 엔드포인트(incoming webhook)로 메시지를 보낸다. 중요한 것은 도구가 아니라 **인지 구간이 확인 주기에서 분리된다**는 구조적 변화다.

다만 푸시는 인지 구간을 줄일 뿐, 분류와 처리 구간은 그대로 남는다. 그리고 잘못 설계하면 새로운 비용인 알림 과잉을 만든다. 아래 세 가지가 그 설계 요소다.

## 라우팅: 맞는 사람에게 보낸다

모든 이슈 알림을 하나의 채널에 쏟으면 누구도 자기 일이라고 느끼지 않는다. 알림은 수신자가 "이건 내가 볼 일"이라고 바로 판단할 수 있어야 대응으로 이어진다.

Google SRE 책의 실용적 알림 장도 알림 관리 계층이 알림을 올바른 목적지로 라우팅하는 역할을 맡고, 같은 알림의 중복을 제거하며, 긴급도에 따라 즉시 호출할 알림은 온콜 담당자에게, 중요하지만 덜 급한 알림은 티켓 큐로 보내는 구성을 소개한다.

이슈 알림에 적용하면 다음과 같은 기준이 된다.

| 조건 | 목적지 |
|---|---|
| 심각도 높음 (서비스 중단, 결제 오류) | 담당 팀 채널 + 담당자 개인 멘션 |
| 컴포넌트가 지정된 일반 이슈 | 해당 컴포넌트 팀 채널 |
| 컴포넌트 미지정 | 분류 담당자 채널 |
| 담당자의 이슈 상태 변경, 댓글 | 담당자와 보고자에게만 |
| 일반 정보성 변경 | 알림 없이 일일 요약 |

라우팅 기준은 이슈 필드에서 나온다. 컴포넌트, 심각도, 이슈 유형이 일관되게 채워지지 않으면 라우팅도 동작하지 않는다. 티켓 작성 규칙이 알림 연동의 전제가 되는 이유다.

## 페이로드: 트래커를 열지 않고도 분류할 수 있게

"새 이슈가 등록되었습니다 #1234" 같은 알림은 결국 사람을 트래커로 보내서 다시 읽게 만든다. 알림 하나에 분류에 필요한 정보가 담겨 있으면 수신자는 메신저 안에서 바로 "내가 지금 볼 일인가"를 판단할 수 있다.

알림 페이로드에 담을 항목의 예다. 특정 메신저의 메시지 포맷이 아니라, 중계 서버가 만들어 낼 내용을 일반적인 구조로 적은 것이다.

```json
{
  "event": "issue_created",
  "issue": {
    "id": 1234,
    "url": "https://tracker.example.com/issues/1234",
    "title": "결제 완료 후 아이템 미지급",
    "type": "bug",
    "severity": "high",
    "component": "payment",
    "environment": "production",
    "reporter": "qa-team",
    "assignee": null,
    "summary": "특정 결제 수단으로 결제 시 영수증 검증 후 아이템 지급 단계에서 실패. 재현율 약 30%."
  },
  "routing": {
    "channel": "payment-team",
    "mention": ["payment-oncall"]
  }
}
```

수신자가 알림만 보고 판단하는 데 필요한 것은 대체로 다음과 같다.

- **무엇이**: 제목과 한두 줄 요약
- **얼마나 심각한가**: 심각도, 영향 범위, 환경(운영인지 개발인지)
- **누구의 일인가**: 컴포넌트, 현재 담당자
- **어디서 더 보나**: 이슈 링크

반대로 본문 전체, 첨부 로그, 모든 필드 변경 이력을 넣으면 알림이 읽히지 않는다. 요약은 짧게 두고 상세는 링크로 넘긴다.

## 알림 피로와 행동 가능한 알림

푸시 방식의 가장 큰 위험은 알림 피로(alert fatigue)다. Google SRE 책의 분산 시스템 모니터링 장은 호출이 너무 잦으면 사람들이 알림을 의심하고, 대충 훑거나, 아예 무시하게 된다고 지적한다. 그리고 다음 원칙을 제시한다.

- 호출이 울릴 때마다 긴급하게 반응할 수 있어야 한다.
- 모든 호출은 행동 가능(actionable)해야 한다.
- 모든 호출에 대한 대응은 사람의 판단을 필요로 해야 한다. 기계적으로 처리되는 대응이 반복된다면 경고 신호다.

같은 장은 새 알림 규칙을 만들 때 던질 질문도 제시한다. 그중 이슈 알림에 그대로 옮길 수 있는 것은 다음과 같다.

- 무해하다는 걸 알고 이 알림을 무시하게 될 일이 있는가?
- 이 알림을 받고 실제로 조치를 취할 수 있는가?
- 같은 문제로 다른 사람도 알림을 받고 있어서, 적어도 하나는 불필요하지 않은가?

SRE 책의 원칙은 장애 호출(page)에 대한 것이지만 이슈 알림에도 그대로 적용된다. 알림 하나하나가 "받은 사람이 무언가를 결정해야 하는 것"이어야 하고, 그렇지 않은 변경은 요약으로 묶거나 보내지 않는다. 기계적 대응만 필요한 알림은 자동화 대상이다.

## 개선을 측정한다

연동의 효과는 체감이 아니라 수치로 확인해야 한다. 업무 이슈에서는 MTTA에 대응하는 지표로 **생성부터 첫 응답까지의 시간**을 쓴다. 첫 응답은 담당자 배정, 상태 변경, 첫 댓글 중 가장 이른 시점으로 정의한다.

측정 시 주의할 점은 다음과 같다.

- **연동 전 기준값을 남긴다**: 트래커의 이벤트 이력에서 과거 이슈의 생성 시각과 첫 응답 시각을 추출해 둔다.
- **평균보다 분포를 본다**: 대부분 빨리 처리되고 일부가 몇 주씩 방치된다면 평균은 현실을 가린다. 중앙값과 85·95 백분위를 함께 본다.
- **심각도별로 나눈다**: 높은 심각도의 첫 응답 시간이 줄었는지가 가장 중요하다.
- **구간별로 본다**: 첫 응답은 빨라졌는데 해결 시간이 그대로라면 병목은 인지가 아니라 처리 단계로 옮겨 간 것이다.
- **알림 대비 조치 비율을 본다**: 알림 수는 늘었는데 조치로 이어진 비율이 낮다면 라우팅이나 필터가 너무 넓다.

인지 구간이 확인 주기에 묶여 있던 팀이라면, 푸시 방식 도입만으로 첫 응답 시간이 "주 단위"에서 "일 단위" 이하로 내려가는 변화를 기대할 수 있다. 확인 주기라는 하한 자체가 사라지기 때문이다.

## 정리

1. 이슈 대응 시간에는 고치는 시간 앞에 인지 시간이 있고, 이 구간은 정보 전달 구조가 결정한다.
2. 풀 방식에서는 사람의 확인 주기가 대응 시간의 하한이 되며, 바쁠수록 길어진다.
3. 웹훅 기반 푸시는 인지를 이벤트 시점으로 당기지만, 분류와 처리 구간은 그대로 남는다.
4. 라우팅으로 맞는 사람에게 보내고, 페이로드에 분류 정보를 담아 트래커를 열지 않고도 판단하게 한다.
5. 모든 알림은 행동 가능해야 한다. 그렇지 않은 알림은 요약으로 묶거나 없앤다.
6. 생성부터 첫 응답까지의 시간을 연동 전후로 분포와 심각도별로 비교해 효과를 확인한다.
