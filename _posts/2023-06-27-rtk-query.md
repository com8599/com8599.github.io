Redux로 API 데이터를 다루면 `isLoading`, `error`, `data`를 담는 slice와 thunk를 엔드포인트마다 반복해서 만들게 된다. 같은 데이터를 두 화면에서 요청하면 요청이 두 번 나가고, 수정 후에는 어떤 목록을 다시 불러와야 하는지 직접 기억해야 한다. RTK Query는 Redux Toolkit(1.9 기준 `@reduxjs/toolkit/query`)에 포함된 데이터 패칭·캐싱 도구로, 이 반복을 API 정의 한 곳으로 모은다.

## 클라이언트 상태와 서버 상태

상태는 소유자가 누구냐에 따라 성격이 다르다.

| 구분 | 클라이언트 상태 | 서버 상태 |
|---|---|---|
| 예 | 모달 열림 여부, 선택된 탭, 폼 입력값 | 사용자 목록, 주문 상세, 권한 정보 |
| 원본 위치 | 브라우저 메모리 | 서버 데이터베이스 |
| 변경 주체 | 현재 사용자 한 명 | 다른 사용자, 배치 작업 등 여러 주체 |
| 신선도 | 항상 최신 | 받은 순간부터 낡을 수 있음 |
| 필요한 처리 | 동기적 갱신 | 로딩/에러 상태, 중복 요청 제거, 캐시 만료, 재요청 |

서버 상태는 클라이언트가 가진 것이 **사본(cache)**일 뿐이다. 그래서 "언제 다시 가져올지", "얼마나 보관할지", "수정 후 어떤 사본을 버릴지"가 핵심 문제가 된다. RTK Query는 이 문제를 엔드포인트 정의와 태그로 해결하고, 클라이언트 상태는 기존처럼 `createSlice`로 관리한다.

## API slice 정의

`createApi`로 서버와 통신하는 방법(baseQuery)과 엔드포인트 목록을 한 번에 정의한다. React 훅을 자동 생성하려면 `@reduxjs/toolkit/query/react`에서 가져온다.

```ts
// services/api.ts
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';
import type { RootState } from '../store';

export interface User {
  id: number;
  name: string;
  role: 'admin' | 'staff';
}

export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({
    baseUrl: '/api',
    prepareHeaders: (headers, { getState }) => {
      const token = (getState() as RootState).auth.accessToken;
      if (token) headers.set('authorization', `Bearer ${token}`);
      return headers;
    },
  }),
  tagTypes: ['User'],
  endpoints: (build) => ({
    getUsers: build.query<User[], { page: number }>({
      query: ({ page }) => `users?page=${page}`,
    }),
    getUser: build.query<User, number>({
      query: (id) => `users/${id}`,
    }),
    updateUser: build.mutation<User, Pick<User, 'id'> & Partial<User>>({
      query: ({ id, ...patch }) => ({
        url: `users/${id}`,
        method: 'PATCH',
        body: patch,
      }),
    }),
  }),
});

export const { useGetUsersQuery, useGetUserQuery, useUpdateUserMutation } = api;
```

- `fetchBaseQuery`는 `fetch`를 감싼 기본 baseQuery다. `baseUrl`, `prepareHeaders` 등으로 공통 설정을 한다.
- `build.query`는 데이터를 읽는 엔드포인트, `build.mutation`은 서버 데이터를 바꾸는 엔드포인트다.
- 엔드포인트 이름에서 훅 이름이 만들어진다. `getUsers` → `useGetUsersQuery`, `updateUser` → `useUpdateUserMutation`. 수동으로 실행하는 `useLazyGetUsersQuery`도 함께 생긴다.

## store 연결

API slice는 reducer와 middleware를 함께 제공한다. reducer는 캐시를 저장하고, middleware는 구독 수 계산, 캐시 만료, 태그 무효화, 폴링(polling)을 처리하므로 둘 다 등록해야 한다.

```ts
// store.ts
import { configureStore } from '@reduxjs/toolkit';
import { setupListeners } from '@reduxjs/toolkit/query';
import { api } from './services/api';
import authReducer from './features/authSlice';

export const store = configureStore({
  reducer: {
    auth: authReducer,
    [api.reducerPath]: api.reducer,
  },
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware().concat(api.middleware),
});

setupListeners(store.dispatch);

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

`reducerPath`는 store 안에서 캐시가 놓일 키이며 기본값은 `'api'`다. `createApi`를 여러 번 호출한다면 각각 다른 값을 줘야 한다. 다만 공식 문서는 서버(base URL) 하나당 API slice 하나를 두고, 엔드포인트가 많아지면 `injectEndpoints`로 파일을 나누는 방식을 권장한다.

## 훅 사용

```tsx
import { useState } from 'react';
import { useGetUsersQuery, useUpdateUserMutation } from './services/api';

export function UserList() {
  const [page, setPage] = useState(1);
  const { data, error, isLoading, isFetching, refetch } = useGetUsersQuery({ page });
  const [updateUser, { isLoading: isSaving }] = useUpdateUserMutation();

  const promote = async (id: number) => {
    try {
      await updateUser({ id, role: 'admin' }).unwrap();
    } catch (e) {
      // unwrap()은 실패 시 에러를 throw한다
    }
  };

  if (isLoading) return <p>불러오는 중</p>;
  if (error) return <button onClick={refetch}>다시 시도</button>;

  return (
    <section>
      <ul className={isFetching ? 'list list--dim' : 'list'}>
        {data?.map((user) => (
          <li key={user.id}>
            {user.name}
            <button disabled={isSaving} onClick={() => promote(user.id)}>
              관리자로 변경
            </button>
          </li>
        ))}
      </ul>
      <button onClick={() => setPage((p) => p + 1)}>다음</button>
    </section>
  );
}
```

| 플래그 | 의미 |
|---|---|
| `isLoading` | 이 훅에 아직 데이터가 없는 상태에서 첫 요청 중 |
| `isFetching` | 첫 요청이든 재요청이든 요청이 진행 중 |
| `isSuccess` / `isError` | 마지막 요청 결과 |
| `currentData` | 현재 인자에 해당하는 데이터(인자가 바뀌어 로딩 중이면 `undefined`) |

페이지를 바꾸면 `data`는 새 응답이 올 때까지 이전 페이지 값을 유지하고 `isFetching`만 `true`가 된다. 깜빡임 없이 목록을 흐리게 처리할 수 있는 이유다. 조건이 갖춰지기 전에는 `skip` 옵션이나 `skipToken`으로 요청을 막는다.

## 캐시 키와 수명

RTK Query는 **엔드포인트 이름 + 직렬화한 인자**를 캐시 키로 쓴다. 기본 `serializeQueryArgs`는 객체 키를 정렬한 뒤 문자열로 만들어 엔드포인트 이름과 합치므로, `{ page: 1, size: 20 }`과 `{ size: 20, page: 1 }`은 같은 캐시를 가리킨다.

- 같은 키를 쓰는 컴포넌트가 여러 개여도 요청은 한 번만 나가고 결과를 공유한다(중복 제거, deduplication).
- 캐시 항목은 구독 수를 센다(reference counting). 구독하는 컴포넌트가 하나라도 있으면 데이터는 유지된다.
- 마지막 구독이 사라지면 타이머가 시작되고, `keepUnusedDataFor`(기본 **60초**) 안에 다시 구독되지 않으면 캐시에서 제거된다.
- 캐시는 응답 단위로 저장된다. 목록과 상세에 같은 사용자가 들어 있어도 별도로 저장되며, 정규화(normalization)하지 않는다.

```ts
export const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  keepUnusedDataFor: 30,
  endpoints: (build) => ({
    getCodes: build.query<string[], void>({
      query: () => 'codes',
      keepUnusedDataFor: 600,
    }),
  }),
});
```

엔드포인트 단위 설정이 API 전체 설정보다 우선한다. 단위는 초다.

## 다시 가져오는 시점

기본적으로 캐시에 데이터가 있으면 새로 구독해도 요청하지 않는다. 다음 옵션으로 재요청 시점을 정한다. `refetch*` 옵션은 `createApi`와 훅 옵션 양쪽에 지정할 수 있고, 훅에 준 값이 우선한다.

| 옵션 | 기본값 | 동작 |
|---|---|---|
| `refetchOnMountOrArgChange` | `false` | `true`면 새 구독자가 생길 때마다 재요청, 숫자(초)면 마지막 응답 후 그 시간이 지났을 때만 재요청 |
| `refetchOnFocus` | `false` | 창이 다시 포커스를 얻으면 구독 중인 쿼리 재요청 |
| `refetchOnReconnect` | `false` | 네트워크 재연결 시 구독 중인 쿼리 재요청 |
| `pollingInterval` | 없음(훅 옵션) | 밀리초 간격으로 주기적 재요청 |

`refetchOnFocus`와 `refetchOnReconnect`는 `setupListeners(store.dispatch)`를 호출해야 동작한다. 이 함수가 `focus`, `visibilitychange`, `online`, `offline` 이벤트를 듣고 액션을 디스패치하기 때문이다.

```tsx
const { data } = useGetUserQuery(id, {
  refetchOnMountOrArgChange: 30,
  refetchOnFocus: true,
});
```

## 태그 기반 무효화

수정 후 "어떤 캐시가 낡았는가"를 선언적으로 연결하는 장치가 태그(tag)다. 쿼리는 `providesTags`로 자기 데이터에 태그를 붙이고, 뮤테이션은 `invalidatesTags`로 태그를 무효화한다.

```ts
export const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['User'],
  endpoints: (build) => ({
    getUsers: build.query<User[], { page: number }>({
      query: ({ page }) => `users?page=${page}`,
      providesTags: (result) =>
        result
          ? [
              ...result.map(({ id }) => ({ type: 'User' as const, id })),
              { type: 'User', id: 'LIST' },
            ]
          : [{ type: 'User', id: 'LIST' }],
    }),
    getUser: build.query<User, number>({
      query: (id) => `users/${id}`,
      providesTags: (result, error, id) => [{ type: 'User', id }],
    }),
    addUser: build.mutation<User, Omit<User, 'id'>>({
      query: (body) => ({ url: 'users', method: 'POST', body }),
      invalidatesTags: [{ type: 'User', id: 'LIST' }],
    }),
    updateUser: build.mutation<User, Pick<User, 'id'> & Partial<User>>({
      query: ({ id, ...patch }) => ({ url: `users/${id}`, method: 'PATCH', body: patch }),
      invalidatesTags: (result, error, arg) => [{ type: 'User', id: arg.id }],
    }),
  }),
});
```

- 사용자를 추가하면 `LIST` 태그만 무효화되므로 목록만 다시 가져오고, 열려 있는 상세는 그대로 둔다.
- 사용자를 수정하면 해당 id 태그를 가진 목록 페이지와 상세가 함께 무효화된다.
- 무효화된 캐시를 구독 중인 컴포넌트가 있으면 즉시 재요청하고, 구독자가 없으면 캐시를 제거해 다음 구독 때 새로 가져온다.
- `'LIST'`는 임의 문자열이다. 실제 id와 겹치지 않는 값을 쓴다.
- 태그 함수는 `(result, error, arg)`를 받는다. 요청이 실패해 `result`가 없을 때도 태그를 돌려주도록 작성해야 한다.

## 401에서 토큰 재발급 후 재시도

Axios 인터셉터(interceptor)처럼 공통 인증 처리를 하려면 baseQuery를 감싼다. 공식 문서의 "Automatic re-authorization by extending fetchBaseQuery" 패턴은 401을 받으면 토큰 갱신 요청을 보내고, 성공하면 원래 요청을 다시 보낸다.

```ts
import { fetchBaseQuery } from '@reduxjs/toolkit/query/react';
import type { BaseQueryFn, FetchArgs, FetchBaseQueryError } from '@reduxjs/toolkit/query';
import { Mutex } from 'async-mutex';
import { tokenReceived, loggedOut } from '../features/authSlice';

const mutex = new Mutex();
const rawBaseQuery = fetchBaseQuery({ baseUrl: '/api', credentials: 'include' });

export const baseQueryWithReauth: BaseQueryFn<
  string | FetchArgs,
  unknown,
  FetchBaseQueryError
> = async (args, api, extraOptions) => {
  await mutex.waitForUnlock();
  let result = await rawBaseQuery(args, api, extraOptions);

  if (result.error && result.error.status === 401) {
    if (!mutex.isLocked()) {
      const release = await mutex.acquire();
      try {
        const refresh = await rawBaseQuery(
          { url: '/auth/refresh', method: 'POST' },
          api,
          extraOptions,
        );
        if (refresh.data) {
          api.dispatch(tokenReceived(refresh.data));
          result = await rawBaseQuery(args, api, extraOptions);
        } else {
          api.dispatch(loggedOut());
        }
      } finally {
        release();
      }
    } else {
      await mutex.waitForUnlock();
      result = await rawBaseQuery(args, api, extraOptions);
    }
  }
  return result;
};
```

뮤텍스(mutex)가 필요한 이유는 동시 요청이다. 화면 하나가 쿼리 다섯 개를 동시에 보내고 토큰이 만료돼 있으면 401이 다섯 번 온다. 뮤텍스가 없으면 갱신 요청도 다섯 번 나가고, 리프레시 토큰을 한 번만 쓰게 하는(rotation) 서버에서는 두 번째 갱신부터 실패해 로그아웃된다. 위 코드는 처음 401을 받은 요청만 락을 잡고 갱신하며, 나머지는 락이 풀리기를 기다렸다가 새 토큰으로 재시도한다.

작성한 함수는 `createApi({ baseQuery: baseQueryWithReauth, ... })`로 연결한다. 갱신 엔드포인트 자체가 401을 반환할 때 다시 갱신을 시도하지 않도록, 갱신 요청은 감싸지 않은 `rawBaseQuery`로 보낸다.

## 낙관적 업데이트

낙관적 업데이트(optimistic update)는 서버 응답 전에 캐시를 먼저 바꾸고, 실패하면 되돌리는 방식이다. 토글처럼 실패 가능성이 낮고 즉각적인 반응이 중요한 동작에 쓴다. `onQueryStarted`는 요청이 시작될 때 호출되며 `queryFulfilled` Promise로 결과를 기다릴 수 있다.

```ts
updateUser: build.mutation<User, Pick<User, 'id'> & Partial<User>>({
  query: ({ id, ...patch }) => ({ url: `users/${id}`, method: 'PATCH', body: patch }),
  async onQueryStarted({ id, ...patch }, { dispatch, queryFulfilled }) {
    const patchResult = dispatch(
      api.util.updateQueryData('getUser', id, (draft) => {
        Object.assign(draft, patch);
      }),
    );
    try {
      await queryFulfilled;
    } catch {
      patchResult.undo();
    }
  },
}),
```

- `updateQueryData(엔드포인트, 인자, 레시피)`는 해당 캐시 항목을 Immer 초안(draft)으로 수정하고, 되돌리기용 패치를 담은 객체를 반환한다.
- 인자는 캐시 키를 찾는 데 쓰이므로 쿼리를 호출할 때와 같은 값을 넘겨야 한다. 목록 캐시(`getUsers({ page })`)까지 바꾸려면 페이지별로 따로 호출해야 한다.
- 실패 시 `undo()` 대신 `dispatch(api.util.invalidateTags([{ type: 'User', id }]))`로 서버 값을 다시 가져오는 방법도 있다. 같은 항목에 뮤테이션이 연달아 겹치면 되돌리기가 꼬일 수 있으므로 재요청이 더 단순하다.

응답을 받은 뒤 그 값으로 캐시를 고치는 비관적 업데이트(pessimistic update)는 `const { data } = await queryFulfilled` 다음에 `updateQueryData`를 호출하면 된다.

## React Query와 비교

RTK Query는 React Query(TanStack Query), SWR 등이 정리한 개념을 바탕으로 Redux 위에 새로 작성한 도구다. 둘 다 서버 상태 캐시라는 같은 문제를 푼다.

| 항목 | RTK Query (RTK 1.9) | React Query (v4) |
|---|---|---|
| 정의 위치 | API slice 한 곳에 엔드포인트를 미리 정의 | 컴포넌트나 커스텀 훅에서 그때그때 정의 |
| 캐시 키 | 엔드포인트 이름 + 직렬화한 인자(자동) | 사용자가 지정한 query key |
| 무효화 | 태그(type/id)로 선언 | `queryClient.invalidateQueries`로 key 지정 |
| 기본 신선도 | 캐시가 있으면 재요청하지 않음 | `staleTime` 기본 0, 마운트·포커스·재연결 시 재요청 |
| 미사용 캐시 보관 | `keepUnusedDataFor` 60초 | `cacheTime` 5분 |
| 실패 재시도 | 기본 없음(`retry` 유틸로 감쌈) | 기본 3회, 지수 백오프 |
| 상태 저장 위치 | Redux store(DevTools에 액션이 보임) | 별도 QueryClient |
| 정규화 캐시 | 없음 | 없음 |

이미 Redux를 쓰고 있고, 캐시 결과를 reducer나 React 밖의 로직에서도 다뤄야 한다면 RTK Query가 자연스럽다. Redux가 없는 프로젝트에 서버 상태 캐시만 필요하다면 React Query가 도입 비용이 더 적다.

## 정리

- 서버 상태는 서버 데이터의 사본이다. 클라이언트 상태와 분리해 캐시 정책으로 관리한다.
- `createApi`에 baseQuery와 엔드포인트를 정의하면 reducer, middleware, 훅이 생성된다. store에는 reducer와 middleware를 모두 등록한다.
- 캐시 키는 엔드포인트 이름과 직렬화한 인자다. 구독이 0이 된 뒤 `keepUnusedDataFor`(기본 60초)가 지나면 제거된다.
- 재요청 시점은 `refetchOnMountOrArgChange`, `refetchOnFocus`, `refetchOnReconnect`로 정하며, 뒤의 둘은 `setupListeners`가 필요하다.
- 수정 후 갱신은 `providesTags`/`invalidatesTags`로 선언한다. `LIST` 태그로 목록과 상세의 무효화 범위를 나눈다.
- 401 재인증은 baseQuery를 감싸 처리하고, 동시 401에 대비해 뮤텍스로 갱신 요청을 하나로 묶는다.
- 낙관적 업데이트는 `onQueryStarted`에서 `updateQueryData`로 캐시를 바꾸고, 실패하면 `undo()`나 태그 무효화로 복구한다.
