같은 기능을 같은 사람이 만들어도, 한 덩어리로 만들어 한 번에 배포할 때와 여러 조각으로 나눠 차례로 배포할 때 사용자에게 닿는 시점이 다르다. 직관적으로는 총 작업량이 같으니 끝나는 시점도 같아야 할 것 같지만, 실제로는 큰 일감이 대기열, 리뷰, 통합, 장애 복구의 모든 단계에서 시간을 더 쓴다. 이 글은 일감 크기, 즉 배치 크기(Batch Size)가 리드 타임에 영향을 주는 경로를 정리한다. 대기 시간이 리드 타임의 대부분을 차지한다는 흐름 효율 관점과 WIP 제한은 앞선 글에서 다뤘으므로 여기서는 반복하지 않는다.

## 두 가지 리드 타임

리드 타임이라는 말은 두 범위로 쓰인다. 섞어 쓰면 지표를 잘못 읽는다.

| 구분 | 시작 | 끝 | 주로 쓰는 곳 |
|---|---|---|---|
| 일감 리드 타임 | 요청(티켓) 생성 | 완료 또는 배포 | 칸반, 서비스 수준 기대치 |
| 변경 리드 타임(Change Lead Time) | 버전 관리에 커밋 | 운영 환경 배포 | DORA 지표 |

일감 리드 타임은 요청자가 체감하는 시간이고, 변경 리드 타임은 코드가 만들어진 뒤 배포 파이프라인과 리뷰를 통과하는 시간이다. 일감을 작게 나누면 두 값이 함께 줄어든다.

## 리틀의 법칙을 일감에 적용하기

리틀의 법칙(Little's Law)은 대기열 이론의 기본 관계식으로, 안정된 시스템에서 다음이 성립한다.

```text
평균 WIP = 평균 처리율(throughput) × 평균 리드 타임
평균 리드 타임 = 평균 WIP ÷ 평균 처리율
```

원래 형태는 L = λW(평균 대기 항목 수 = 평균 도착률 × 평균 체류 시간)이다. 일감에 적용할 때는 도착률 대신 처리율을 쓰는데, 이는 측정 구간에서 들어오는 양과 나가는 양이 평균적으로 같다는 가정이 있을 때만 맞다. 성립 조건은 다음과 같다.

- 측정 구간의 시작과 끝에서 WIP가 크게 다르지 않다(정상 상태).
- 들어온 일감은 결국 완료되거나 명시적으로 빠져나간다. 조용히 버려진 티켓이 보드에 남아 있으면 안 된다.
- WIP, 처리율, 리드 타임을 같은 단위와 같은 기간으로 측정한다.

이 식은 **평균 사이의 관계**이지 개별 티켓의 예측 공식이 아니다. 그래도 방향은 분명하다. 처리율이 같다면 동시에 열린 일감이 많을수록 평균 리드 타임은 길어진다. 그리고 큰 일감은 하나가 오래 열려 있으므로, 같은 사람 수로도 시스템 안에 머무는 "작업량"을 키운다.

여기서 주의할 점은 단위다. 큰 티켓 1개와 작은 티켓 5개가 같은 작업량이라도, 티켓 개수로 센 WIP와 처리율은 다르게 나온다. 리틀의 법칙을 지표로 쓰려면 일감 크기가 어느 정도 고른 편이 좋고, 이것 자체가 일감을 비슷한 크기로 쪼개는 이유가 된다.

## 큰 일감은 변동성을 키운다

평균만큼 중요한 것이 변동성이다. 큰 일감은 추정이 틀릴 여지가 크고, 틀렸을 때의 절대 오차도 크다. 하루짜리 일감이 두 배 걸리면 하루가 밀리지만, 3주짜리 일감이 두 배 걸리면 3주가 밀린다.

대기열 이론은 대기 시간이 이용률(utilization)과 변동성에 따라 커진다고 본다. 가장 단순한 M/M/1 모델에서 평균 대기 시간은 ρ/(1−ρ)에 비례하므로, 이용률 ρ가 80%에서 90%로 오르면 대기 시간은 두 배 이상이 된다. 실제 팀은 이 모델을 그대로 따르지 않지만, 큰 일감이 섞이면 처리 시간의 분포 꼬리가 길어지고 그 뒤에 선 작업들이 함께 기다린다는 성질은 같다. 일감 크기를 고르게 작게 유지하면 리드 타임의 평균뿐 아니라 85번째 백분위 같은 꼬리 값이 줄어, 요청자에게 약속할 수 있는 기한이 짧아진다.

## DORA 지표와 배치 크기

DORA(DevOps Research and Assessment)는 소프트웨어 전달 성과를 네 지표로 측정한다. 2023년 보고서 기준의 이름과 정의는 다음과 같다.

| 지표 | 정의 | 구분 |
|---|---|---|
| 배포 빈도(Deployment Frequency) | 일정 기간의 배포 횟수 또는 배포 사이 간격 | 처리량 |
| 변경 리드 타임(Change Lead Time) | 버전 관리에 커밋된 변경이 운영에 배포되기까지의 시간 | 처리량 |
| 변경 실패율(Change Failure Rate) | 배포 후 즉시 조치가 필요했던 배포의 비율 | 안정성 |
| 실패한 배포의 복구 시간(Failed Deployment Recovery Time) | 즉시 조치가 필요한 실패 배포에서 회복하는 데 걸린 시간 | 안정성 |

마지막 지표는 2023년 보고서에서 이전의 평균 복구 시간(MTTR, Time to Restore Service)을 바꾼 것이다. 모든 장애가 아니라 **배포로 인한 실패**에서의 복구로 범위를 좁혔다.

DORA의 "작은 배치로 일하기(Working in small batches)" 역량 문서는 작은 배치를 지속적 통합과 트렁크 기반 개발의 필요조건으로 본다. 기능은 며칠 안에 개발할 수 있어야 하고, 완료와 검증까지 일주일 넘게 걸리는 코드 묶음은 너무 크다고 말한다. 네 지표와의 관계를 정리하면 다음과 같다.

- 일감이 작으면 커밋에서 배포까지 막히는 지점이 적어 **변경 리드 타임**이 줄고, 배포할 거리가 자주 생겨 **배포 빈도**가 오른다.
- 배포 하나에 담긴 변경이 적으면 실패했을 때 원인을 찾을 범위가 좁고 되돌리기 쉬워 **복구 시간**이 준다.
- 큰 배포는 여러 변경의 상호작용을 한 번에 검증해야 하므로 실패할 여지가 커진다.

## 작은 PR과 리뷰 대기

배치 크기는 코드 리뷰에서 가장 직접적으로 드러난다. Google 엔지니어링 관행 문서는 작은 변경이 더 빨리, 더 꼼꼼하게 리뷰되고, 버그를 만들 가능성이 낮고, 거절되어도 버려지는 작업이 적고, 되돌리기 쉽다고 정리한다. 기준으로는 약 100줄이면 적당하고 약 1000줄은 대개 너무 크다고 제시하며, 리뷰어가 크기만을 이유로 변경을 거절할 수 있다고 쓴다. 같은 문서는 리뷰 요청에 응답하는 데 걸리는 시간이 **최대 1영업일**이어야 한다고 말한다.

큰 PR은 두 번 느리다. 리뷰어는 긴 시간을 확보할 수 있을 때까지 리뷰를 미루고, 막상 리뷰가 시작되면 코멘트 왕복이 길어진다. 리뷰가 늦는 동안 작성자는 다른 일을 시작하므로 WIP도 함께 늘어난다. 작은 PR은 리뷰어가 일정 사이사이에 처리할 수 있어 대기열에 머무는 시간 자체가 짧다.

## 수직 분할과 INVEST

Bill Wake는 2003년 글에서 좋은 사용자 스토리의 조건을 INVEST로 정리했다.

| 글자 | 의미 |
|---|---|
| I | Independent: 다른 스토리와 독립적이다 |
| N | Negotiable: 세부 내용은 협의 가능하다 |
| V | Valuable: 사용자에게 가치가 있다 |
| E | Estimable: 크기를 추정할 수 있다 |
| S | Small: 작다 |
| T | Testable: 검증할 수 있다 |

같은 글은 스토리를 네트워크, 저장, 로직, 화면이 쌓인 여러 층 케이크에 비유하고, 쪼갤 때는 **층을 가로로 자르지 말고 세로로 잘라** 각 조각이 사용자에게 가치를 주게 하라고 한다. "DB 테이블 만들기", "API 만들기", "화면 만들기"로 나누면 각 조각은 작지만 셋이 모두 끝나기 전에는 아무것도 배포할 수 없다. 수평 분할은 배치를 작게 만드는 것처럼 보이지만 배포 단위는 여전히 크다.

## 쪼개는 패턴

수직으로 자르는 대표적인 방법은 다음과 같다.

| 패턴 | 예: "주문 취소 기능" |
|---|---|
| 정상 경로 먼저, 예외는 나중에 | 결제 전 주문 취소 → 결제 후 환불 포함 취소 |
| 규칙 변형별로 | 전액 취소 → 부분 취소 |
| 데이터 변형별로 | 카드 결제 취소 → 간편결제 취소 |
| 작업 흐름 단계별로 | 고객 취소 요청 → 관리자 승인 → 자동 승인 |
| 수동으로 먼저 | 관리자 화면에서 수동 취소 → 고객 셀프 취소 |
| 불확실성 분리 | 결제사 취소 API 조사(시간 상한) → 구현 |

각 조각은 그 자체로 배포할 수 있고 검증 가능한 인수 조건을 가져야 한다. 쪼갠 결과가 "앞 조각이 끝나야 의미가 있는" 순서 의존을 만들더라도, 각 조각이 운영에 배포되어 동작한다면 수직 분할이다.

## 배포와 릴리스를 분리한다

조각이 배포 가능하더라도 사용자에게 보여 주기에는 기능이 덜 갖춰졌을 수 있다. 이때 피처 플래그(Feature Flag)로 배포(deploy)와 릴리스(release)를 분리한다. Pete Hodgson의 피처 토글 글은 이를 지속적 전달의 "기능 릴리스와 코드 배포의 분리" 원칙을 구현하는 가장 흔한 방법으로 설명한다. 미완성 코드를 꺼진 상태로 트렁크에 병합하고 운영에 배포해 두었다가, 준비되면 설정만 바꿔 공개한다.

```typescript
// 릴리스 토글: 꺼져 있으면 기존 동작 그대로
if (flags.isEnabled('order-partial-cancel', { userId })) {
  return this.cancelPartially(order, items);
}
return this.cancelAll(order);
```

같은 글은 토글을 유지 비용이 있는 재고로 본다. 분기와 테스트 조합이 늘기 때문이다. 릴리스 토글은 보통 1~2주 정도만 유지하는 임시 장치이므로, 토글을 만들 때 제거 티켓을 함께 만들거나 만료일을 정한다.

## 비교

| 항목 | 큰 일감 한 번에 | 작은 일감 여러 번 |
|---|---|---|
| 리뷰 | 리뷰 착수가 늦고 왕복이 김 | 일정 사이에 처리, 빠른 피드백 |
| 병합 | 브랜치가 오래 살아 충돌 누적 | 트렁크와의 차이가 작음 |
| 추정 오차 | 절대 오차가 크고 일정 전체가 밀림 | 오차가 작고 다음 조각에서 조정 |
| 배포 실패 | 원인 범위가 넓고 되돌리기 어려움 | 범위가 좁고 되돌리기 쉬움 |
| 피드백 | 완성 후에야 방향 검증 | 첫 조각 배포 후 검증 |
| 비용 | 조율 비용이 적어 보임 | 분할·토글 관리 비용이 듦 |

작은 일감에도 비용은 있다. 티켓 관리, 배포 횟수, 토글 정리가 늘어난다. 이 비용을 낮추는 것이 자동화된 배포 파이프라인이고, 배포 비용이 낮을수록 최적의 배치 크기도 작아진다.

## 정리

1. 리드 타임은 일감 기준(요청→완료)과 변경 기준(커밋→배포)이 있고, 일감을 작게 나누면 둘 다 줄어든다.
2. 리틀의 법칙은 정상 상태에서 평균 WIP = 평균 처리율 × 평균 리드 타임이라는 평균 사이의 관계다. 개별 예측이 아니라 방향을 읽는 데 쓴다.
3. 큰 일감은 평균뿐 아니라 변동성을 키워, 이용률이 높은 팀에서 대기 시간의 꼬리를 길게 만든다.
4. DORA의 배포 빈도, 변경 리드 타임, 변경 실패율, 실패한 배포의 복구 시간은 모두 배치 크기와 연결된다.
5. 스토리는 INVEST 기준으로 세로로 자르고, 미완성 기능은 릴리스 토글로 숨긴 채 배포한다. 토글은 제거 계획과 함께 만든다.
