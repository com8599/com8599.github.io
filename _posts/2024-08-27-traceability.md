운영에서 문제가 생겼을 때 가장 먼저 묻는 것은 "최근에 무엇이 바뀌었나"이고, 그다음은 "왜 바꿨나"다. 첫 질문은 배포 기록과 Git 이력으로 답할 수 있지만, 두 번째 질문의 답은 코드에 없다. 요구사항과 논의는 티켓에, 구현은 커밋에, 검토는 PR에 흩어져 있다. 추적성(Traceability)은 이 셋을 서로 찾아갈 수 있게 연결해 두는 성질이다. 이 글은 연결 규칙과 그 규칙이 장애 대응, 리뷰, 릴리스 노트에서 어떻게 쓰이는지 정리한다. PR 이벤트로 티켓 상태를 자동 전환하는 내용은 앞선 글에서 다뤘으므로 여기서는 연결 자체에 집중한다.

## 연결의 사슬

추적성은 두 방향으로 쓰인다.

```text
정방향:  요구사항 → 티켓 → 브랜치 → 커밋 → PR → 배포
역방향:  배포(이미지 태그) → 커밋 SHA → PR → 티켓 → 요구사항·논의
```

정방향은 "이 요구가 어디까지 진행됐나"를 보는 데 쓰고, 역방향은 "이 코드가 왜 이렇게 되었나"를 보는 데 쓴다. 장애 대응과 코드 리뷰에서 필요한 것은 주로 역방향이다. 사슬의 고리 하나라도 끊기면 그 뒤로는 사람의 기억에 의존해야 한다.

고리를 잇는 공통 키는 티켓 키(예: `SHOP-123`)와 커밋 SHA다. 티켓 키는 사람이 붙이고, SHA는 도구가 붙인다. 사람이 붙이는 쪽을 규칙으로 정하고 가능한 한 자동화하는 것이 핵심이다.

## 티켓 키를 남기는 위치

Atlassian 문서는 Jira 이슈와 개발 작업을 연결하는 방법으로 다음 세 위치를 든다.

| 위치 | 예 | 비고 |
|---|---|---|
| 브랜치 이름 | `SHOP-123-order-partial-cancel` | 브랜치를 만들 때 키를 넣으면 이슈에 연결된다 |
| 커밋 메시지 | `SHOP-123 부분 취소 금액 계산 추가` | 커밋 단위로 연결된다 |
| PR 제목 | `SHOP-123 주문 부분 취소` | 제목에 키가 있으면 자동으로 연결된다 |

이슈 키는 대문자로 써야 인식된다(`shop-123`은 안 된다). 연결된 브랜치, 커밋, PR은 이슈의 개발(Development) 패널에 모이고, 보드 카드에도 아이콘으로 표시된다. GitHub, GitLab, Bitbucket 같은 저장소를 Jira에 연결해 두어야 하며, 저장소에 무언가를 푸시해야 동기화가 시작된다.

### 스마트 커밋(Smart Commits)

Jira는 커밋 메시지 안의 명령으로 이슈를 조작하는 스마트 커밋을 지원한다. 관리자가 기능을 켜야 하고, 커밋 작성자의 이메일이 권한 있는 Jira 사용자 한 명과 정확히 일치해야 동작한다. 일치하지 않아도 커밋은 성공하지만 명령은 실행되지 않는다.

```bash
git commit -m "SHOP-123 #comment 부분 취소 금액 계산 추가"
git commit -m "SHOP-123 #time 2h 30m 환불 금액 검증"
git commit -m "SHOP-123 #close #comment 리뷰 반영 완료"
```

`#comment`, `#time`, 그리고 `#` 뒤에 워크플로 전환 이름을 쓰는 세 종류가 있다. 전환 이름은 첫 공백 앞부분으로 매칭되므로 모호하면 `#start-review`처럼 하이픈으로 이어 쓴다. 명령은 한 줄에 있어야 하고, `git push --force`나 스쿼시 병합처럼 이력을 다시 쓰면 같은 명령이 다시 처리되어 중복 기록이 생길 수 있다. Atlassian은 PR 제목에 스마트 커밋 명령을 넣지 말라고도 안내한다. 제목이 병합 커밋 메시지가 되기 때문이다. 상태 전환은 PR 이벤트 기반 자동화에 맡기고, 커밋 메시지에는 키만 남기는 편이 단순하다.

### GitHub 자동 링크(Autolink)

GitHub 쪽에서도 티켓 키를 클릭 가능한 링크로 만들 수 있다. 저장소 설정의 자동 링크 참조(autolink reference)에 접두사와 대상 URL을 등록하면, 이슈, PR, 커밋 메시지, 릴리스 설명에 나온 키가 외부 트래커 링크로 바뀐다. URL 안의 `<num>`이 참조 식별자로 치환되고, 식별자 형식은 숫자 전용과 영숫자 중에서 고른다. 저장소 관리자 권한이 있어야 설정할 수 있다.

| 항목 | 값 |
|---|---|
| Reference prefix | `SHOP-` |
| Target URL | `https://example.atlassian.net/browse/SHOP-<num>` |

`SHOP`과 `SHO`처럼 서로 겹치는 접두사는 함께 등록할 수 없다.

## Conventional Commits로 커밋의 의도를 남기기

티켓 키가 "어떤 요구 때문인가"를 연결한다면, 커밋 메시지 형식은 "어떤 종류의 변경인가"를 남긴다. Conventional Commits 1.0.0의 구조는 다음과 같다.

```text
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

명세가 정하는 타입은 `fix`(SemVer의 PATCH에 대응)와 `feat`(MINOR에 대응) 두 가지다. 호환성을 깨는 변경은 타입과 관계없이 `!`를 붙이거나 `BREAKING CHANGE:` 꼬리말로 표시하고 MAJOR에 대응한다. `build`, `chore`, `ci`, `docs`, `refactor`, `perf`, `test` 같은 타입은 Angular 관례에서 온 권장 목록이며 명세가 강제하지는 않는다. 꼬리말은 `토큰: 값` 형식이어서 티켓 키를 넣기에 알맞다.

```text
feat(order): 주문 부분 취소 지원

결제 완료 주문에서 품목 단위로 취소할 수 있다.
환불 금액은 쿠폰 할인을 품목 금액 비율로 나눠 계산한다.

Refs: SHOP-123
```

제목에는 무엇을 바꿨는지, 본문에는 왜 그렇게 바꿨는지를 쓴다. 코드에서 읽을 수 없는 것이 바로 "왜"다.

## 장애 대응에서 거꾸로 따라가기

배포 산출물에 커밋 SHA를 남기는 것이 역방향 추적의 출발점이다. 컨테이너 이미지 태그를 Git SHA로 붙이면, 지금 운영에서 도는 태스크 정의의 이미지 태그만 보고도 정확한 커밋을 알 수 있다.

```bash
# 빌드 시 이미지 태그에 커밋 SHA 사용
docker build -t "$REGISTRY/api:$(git rev-parse --short=12 HEAD)" .

# 직전 배포와 현재 배포 사이에 들어간 커밋과 티켓 키
git log --oneline --no-merges 3f1c2a9b7d10..9e8d7c6b5a43
git log --format='%h %s' 3f1c2a9b7d10..9e8d7c6b5a43 | grep -oE 'SHOP-[0-9]+' | sort -u
```

두 배포 사이의 변경 목록과 티켓 키를 뽑으면 "이번 배포에 포함된 요구사항"이 바로 나온다. 장애 증상과 관련 있어 보이는 티켓에서 요구사항과 논의를 읽고, PR에서 리뷰 코멘트와 테스트 범위를 확인한다. 되돌릴지, 앞으로 고칠지는 이 맥락을 보고 결정한다.

코드 한 줄에서 출발할 때는 `git blame`과 `git log`를 쓴다.

```bash
# 특정 줄 범위를 마지막으로 바꾼 커밋
git blame -L 120,140 src/order/refund.service.ts

# 공백 변경 무시, 다른 파일에서 옮겨 온 줄까지 추적
git blame -w -C -L 120,140 src/order/refund.service.ts

# 특정 문자열이 추가되거나 제거된 커밋 찾기(pickaxe)
git log -S 'calculateRefundRatio' --oneline

# 메시지에 티켓 키가 있는 커밋
git log --grep='SHOP-123' --oneline
```

포매터 일괄 적용 같은 대량 변경 커밋은 blame 결과를 가린다. 그 커밋의 SHA를 `.git-blame-ignore-revs`에 적고 `git config blame.ignoreRevsFile .git-blame-ignore-revs`로 지정하면, 해당 커밋이 바꾼 줄은 그 이전 커밋으로 돌아가 표시된다. GitHub의 blame 화면도 저장소 루트의 이 파일을 읽어 같은 커밋을 숨긴다.

blame이 알려 주는 것은 커밋까지다. 커밋 메시지에 티켓 키가 있고 PR이 그 키로 연결되어 있어야 "왜"까지 갈 수 있다.

## 리뷰에서의 효과

리뷰어가 PR에서 가장 먼저 확인해야 하는 것은 이 변경이 무엇을 해결하려는지다. PR 제목의 티켓 키를 따라가면 인수 조건과 논의가 있으므로, 리뷰어는 코드가 요구를 충족하는지를 기준으로 읽을 수 있다. 반대로 연결이 없으면 리뷰는 코드 스타일과 국소적인 정합성 검토에 머물기 쉽다.

티켓 하나에 PR이 여러 개 연결되는 것은 자연스럽다. 일감을 작게 나눈 결과다. 개발 패널에서 한 이슈에 걸린 PR 목록을 보면 요구사항이 어떤 단계로 구현되었는지가 한눈에 보인다.

## 릴리스 노트 자동 생성

GitHub의 자동 생성 릴리스 노트는 병합된 PR 목록, 기여자 목록, 전체 변경 비교 링크를 만든다. 저장소에 `.github/release.yml`을 두면 PR 라벨로 분류하고 제외할 수 있다.

```yaml
changelog:
  exclude:
    labels:
      - skip-changelog
    authors:
      - dependabot
  categories:
    - title: 호환성 변경
      labels:
        - breaking-change
    - title: 새 기능
      labels:
        - feature
    - title: 버그 수정
      labels:
        - bug
    - title: 기타
      labels:
        - "*"
```

`"*"`는 앞 범주에 해당하지 않은 PR을 모두 받는다. PR 제목에 티켓 키를 넣고 자동 링크를 등록해 두면, 릴리스 설명의 키도 티켓 링크로 바뀌어 릴리스 노트가 곧 "이번 배포에 포함된 요구사항 목록"이 된다. 릴리스 노트의 품질은 결국 PR 제목과 라벨의 품질이다.

## 연결 방식 비교

| 방식 | 연결 대상 | 장점 | 한계 |
|---|---|---|---|
| 브랜치 이름의 키 | 브랜치와 그 PR | 브랜치 생성 시 한 번만 넣으면 됨 | 브랜치가 지워지면 이력에서 사라짐 |
| 커밋 메시지의 키 | 개별 커밋 | `git log`·blame에서 바로 보임, 이력에 영구히 남음 | 모든 커밋에 넣는 규율 필요 |
| PR 제목의 키 | PR 전체 | 리뷰·릴리스 노트와 바로 연결 | 스쿼시 병합 메시지 설정에 따라 커밋에 남지 않을 수 있음 |
| 스마트 커밋 | 이슈 상태·댓글·작업 시간 | 커밋으로 트래커 조작 | 이메일 일치 필요, 이력 재작성 시 중복 처리 |
| GitHub 자동 링크 | GitHub 화면 → 외부 트래커 | 키를 클릭 가능한 링크로 | 트래커 쪽 연결은 별도 연동 필요 |
| Conventional Commits | 변경 종류·호환성 | 릴리스 분류·버전 결정에 활용 | 형식 검사 도구 없이는 지켜지지 않음 |

스쿼시 병합을 쓴다면 PR 제목을 병합 커밋 메시지로 쓰도록 저장소 설정을 맞춰, PR 제목의 티켓 키가 메인 브랜치 이력에 남게 한다.

## 정리

1. 추적성은 배포 → 커밋 → PR → 티켓 → 요구사항으로 거꾸로 따라갈 수 있는 성질이고, 장애 대응과 리뷰에서 "왜"에 답하게 해 준다.
2. 티켓 키는 브랜치 이름, 커밋 메시지, PR 제목에 대문자로 넣는다. 이 중 커밋 메시지는 브랜치가 지워지고 도구를 바꿔도 Git 이력에 그대로 남는다.
3. 스마트 커밋은 편하지만 이메일 일치와 이력 재작성 시 중복 처리를 주의하고, 상태 전환은 PR 이벤트 자동화에 맡기는 편이 단순하다.
4. 이미지 태그를 커밋 SHA로 붙이면 두 배포 사이의 커밋과 티켓 목록을 바로 뽑을 수 있다.
5. `git blame -w -C`, `git log -S`, `.git-blame-ignore-revs`로 코드 한 줄에서 커밋까지 가고, 커밋의 티켓 키로 요구사항까지 간다.
6. `.github/release.yml`과 자동 링크를 함께 쓰면 릴리스 노트가 티켓 목록이 된다.
