이 글은 S3에 업로드된 MP4를 그대로 내려보내는 숏폼 영상 서비스에 HLS(HTTP Live Streaming) 적응형 스트리밍을 도입하기 위한 **설계안**이다. 구현 전에 선택지와 트레이드오프를 정리하고, 어떤 순서로 도입하고 무엇을 측정해 판단할지 정하는 것이 목적이다. 따라서 이 글의 수치는 공식 문서의 권장값이거나 검증이 필요한 초기 가정이며, 측정 결과가 아니다.

## 단일 MP4 재생의 한계

업로드된 원본(또는 한 번 압축한 MP4)을 CDN으로 내려보내는 방식을 흔히 프로그레시브 다운로드(Progressive Download)라고 부른다. 구현이 단순하고, HTTP 범위 요청(Range Request)으로 탐색도 된다. 하지만 숏폼에서는 다음 한계가 드러난다.

| 한계 | 설명 |
|---|---|
| 비트레이트가 하나 | 느린 네트워크에서도 같은 품질을 받아야 하므로 버퍼링이 생기고, 빠른 네트워크에서도 더 좋은 품질로 올라갈 수 없음 |
| 낭비되는 전송량 | 사용자가 몇 초 만에 넘기는 영상도 플레이어가 미리 받아 둔 만큼은 전송됨 |
| 시작 지연 | `moov` 박스가 파일 끝에 있으면 재생 전에 메타데이터를 찾아야 함. 인코딩 시 faststart 처리가 필요 |
| 원본 의존 | 업로드한 기기의 코덱, 해상도, 비트레이트가 그대로 재생 품질과 비용이 됨 |

적응형 스트리밍은 같은 영상을 여러 품질로 미리 인코딩하고 짧은 조각으로 나눈 뒤, 플레이어가 네트워크 상황에 따라 조각 단위로 품질을 바꿔 받게 한다. HLS는 Apple이 만든 방식으로 RFC 8216으로 공개되어 있고, iOS의 AVPlayer와 Android의 ExoPlayer가 기본으로 지원한다. Flutter의 `video_player`도 내부적으로 이 플레이어들을 쓰므로 앱 쪽 변경은 재생 URL 교체가 중심이 된다.

## HLS 플레이리스트 구조

HLS는 텍스트 파일인 플레이리스트(`.m3u8`)와 미디어 세그먼트로 구성된다. 플레이리스트는 두 계층이다.

| 종류 | 내용 | 주요 태그 |
|---|---|---|
| 마스터 플레이리스트(Master Playlist, Apple 문서의 Multivariant Playlist) | 화질별 변형(variant) 목록과 각 변형의 대역폭·해상도·코덱 | `EXT-X-STREAM-INF`, `EXT-X-INDEPENDENT-SEGMENTS` |
| 미디어 플레이리스트(Media Playlist) | 한 변형의 세그먼트 목록과 각 길이 | `EXT-X-TARGETDURATION`, `EXTINF`, `EXT-X-PLAYLIST-TYPE`, `EXT-X-ENDLIST` |

마스터 플레이리스트 예시다.

```text
#EXTM3U
#EXT-X-VERSION:7
#EXT-X-INDEPENDENT-SEGMENTS
#EXT-X-STREAM-INF:BANDWIDTH=900000,AVERAGE-BANDWIDTH=700000,CODECS="avc1.64001f,mp4a.40.2",RESOLUTION=540x960,FRAME-RATE=30.000
540p/index.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=2200000,AVERAGE-BANDWIDTH=1800000,CODECS="avc1.64001f,mp4a.40.2",RESOLUTION=720x1280,FRAME-RATE=30.000
720p/index.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=4500000,AVERAGE-BANDWIDTH=3600000,CODECS="avc1.640028,mp4a.40.2",RESOLUTION=1080x1920,FRAME-RATE=30.000
1080p/index.m3u8
```

미디어 플레이리스트 예시다.

```text
#EXTM3U
#EXT-X-VERSION:7
#EXT-X-TARGETDURATION:6
#EXT-X-PLAYLIST-TYPE:VOD
#EXT-X-MAP:URI="init.mp4"
#EXTINF:6.000,
seg_000.m4s
#EXTINF:6.000,
seg_001.m4s
#EXTINF:3.200,
seg_002.m4s
#EXT-X-ENDLIST
```

- `EXT-X-STREAM-INF`의 `BANDWIDTH`는 필수이며 최대 비트레이트를 뜻한다. Apple 작성 사양은 여기에 `AVERAGE-BANDWIDTH`, `CODECS`, 영상이 있으면 `RESOLUTION`과 `FRAME-RATE`까지 반드시 넣도록 요구한다.
- `EXT-X-TARGETDURATION`은 세그먼트 최대 길이이고, 각 `EXTINF` 값을 정수로 반올림한 값은 이를 넘을 수 없다.
- `EXT-X-PLAYLIST-TYPE:VOD`와 `EXT-X-ENDLIST`는 목록이 더 이상 바뀌지 않는다는 뜻이다. 숏폼은 라이브가 아니므로 VOD로 만든다.
- 세그먼트 컨테이너는 MPEG-TS 또는 fMP4(fragmented MP4)다. fMP4를 쓰면 초기화 세그먼트를 가리키는 `EXT-X-MAP`이 필요하다. H.264는 둘 다 가능하지만 HEVC는 fMP4만 허용되므로, 나중의 코덱 확장을 생각하면 fMP4가 유리하다.

Apple 작성 사양은 이 외에도 탐색(scrubbing) UI를 위한 I-프레임 전용 플레이리스트(`EXT-X-I-FRAME-STREAM-INF`)를 요구한다. 숏폼 피드는 탐색 UI가 거의 없으므로 1차 범위에서는 제외하고, 상세 화면에 탐색 바를 붙일 때 추가한다.

## 비트레이트 사다리(Bitrate Ladder)

변형 목록을 비트레이트 사다리라고 한다. Apple 작성 사양은 16:9 H.264 기준으로 다음과 같은 예시를 든다(단위 kbit/s).

| 해상도(16:9) | 비트레이트 | 프레임레이트 |
|---|---|---|
| 416×234 | 145 | 30fps 이하 |
| 640×360 | 365 | 30fps 이하 |
| 768×432 | 730 / 1100 | 30fps 이하 |
| 960×540 | 2000 | 원본과 동일 |
| 1280×720 | 3000 / 4500 | 원본과 동일 |
| 1920×1080 | 6000 / 7800 | 원본과 동일 |

숏폼은 세로(9:16) 영상이므로 가로·세로를 바꿔 적용하고, 처음에는 단계를 줄여 시작하는 것을 초기안으로 둔다.

| 단계 | 해상도(9:16) | 목표 평균 비트레이트(초기 가정) | 용도 |
|---|---|---|---|
| 1 | 360×640 | 약 400 kbit/s | 저속 모바일 네트워크 |
| 2 | 540×960 | 약 1,000 kbit/s | 기본 시작 품질 후보 |
| 3 | 720×1280 | 약 2,000 kbit/s | 일반 Wi-Fi |
| 4 | 1080×1920 | 약 4,000 kbit/s | 원본이 1080p 이상일 때만 생성 |

이 값들은 Apple 예시를 출발점으로 잡은 가정이다. 숏폼은 화면 대부분이 얼굴과 자막처럼 단순한 장면일 수도, 움직임이 많은 장면일 수도 있어 콘텐츠마다 필요한 비트레이트가 크게 다르다. 원본보다 높은 해상도의 변형은 만들지 않는 규칙과, 샘플 영상으로 화질을 비교해 사다리를 조정하는 단계를 계획에 포함한다. MediaConvert의 자동 ABR(Automated ABR)처럼 콘텐츠를 분석해 사다리를 정해 주는 기능도 비교 대상이다.

## 세그먼트 길이

Apple 작성 사양의 권장은 다음과 같다.

- 목표 길이(target duration)는 6초를 권장(SHOULD)한다.
- 세그먼트는 IDR 프레임으로 시작해야 하고(MUST), 키프레임은 2초마다 두는 것을 권장한다.
- 세그먼트는 목표 길이를 0.5초 넘게 초과하면 안 된다.

| 세그먼트 길이 | 장점 | 단점 |
|---|---|---|
| 짧게 (2초 안팎) | 첫 세그먼트가 작아 시작이 빠를 수 있음, 품질 전환이 빠름 | 요청 수와 플레이리스트 항목 증가, 세그먼트당 오버헤드 비중 증가 |
| 권장값 (6초) | Apple 사양과 일치, 요청 수가 적음, 캐시 효율이 좋음 | 15초 영상이면 세그먼트가 2~3개뿐이라 적응의 여지가 적음 |

숏폼은 영상 자체가 15~60초로 짧고 첫 프레임까지의 시간이 체감 품질을 좌우한다. 그래서 키프레임 간격은 2초로 고정해 두고, 세그먼트 길이는 6초(권장값)와 2초 또는 4초를 실험으로 비교한다. 키프레임 간격을 2초로 맞춰 두면 같은 인코딩 설정에서 세그먼트 길이만 바꿔 다시 패키징할 수 있다. 권장값에서 벗어나는 선택은 측정 결과로 근거를 남긴다.

## 트랜스코딩 방식 비교

업로드된 원본을 사다리대로 인코딩하고 HLS로 패키징하는 단계다. 두 가지 후보를 비교한다.

| 항목 | AWS Elemental MediaConvert | FFmpeg on ECS(Fargate) / AWS Batch |
|---|---|---|
| 운영 | 관리형. 작업(Job) 템플릿만 관리 | 컨테이너 이미지, 큐, 재시도, 스케일링을 직접 관리 |
| 과금 | 출력 영상 길이(분) 기준. 티어, 해상도, 프레임레이트, 코덱에 따라 단가가 다름 | 실행한 vCPU·메모리 시간. 인코딩 속도가 곧 비용 |
| 출력 | Apple HLS 출력 그룹으로 플레이리스트·세그먼트 생성 | `-f hls`, `-var_stream_map`, `-master_pl_name` 등으로 직접 구성 |
| 사다리 결정 | 고정 사다리 또는 자동 ABR | 직접 구현 |
| 이벤트 연동 | 작업 상태 변경이 EventBridge 이벤트로 발행 | 작업 종료를 직접 알리거나 Batch 이벤트 사용 |
| 유연성 | 제공 기능 범위 안에서 설정 | 워터마크, 필터, 썸네일 추출 등 자유 |
| 적합한 경우 | 인코딩 전문 인력이 없고 처리량이 예측하기 어려울 때 | 처리량이 꾸준하고 인코딩 설정을 세밀하게 다루고 싶을 때 |

FFmpeg로 구성할 경우의 명령 골격은 다음과 같다.

```bash
ffmpeg -i input.mp4 \
  -filter_complex "[0:v]split=3[v1][v2][v3];[v1]scale=360:640[v1o];[v2]scale=540:960[v2o];[v3]scale=720:1280[v3o]" \
  -map "[v1o]" -map "[v2o]" -map "[v3o]" -map 0:a -map 0:a -map 0:a \
  -c:v libx264 -preset veryfast -profile:v high \
  -b:v:0 400k -b:v:1 1000k -b:v:2 2000k \
  -g 60 -keyint_min 60 -sc_threshold 0 \
  -c:a aac -b:a 96k \
  -f hls -hls_time 6 -hls_playlist_type vod \
  -hls_segment_type fmp4 -hls_flags independent_segments \
  -master_pl_name master.m3u8 \
  -var_stream_map "v:0,a:0 v:1,a:1 v:2,a:2" \
  -hls_segment_filename "out/%v/seg_%03d.m4s" \
  out/%v/index.m3u8
```

- `-g 60 -keyint_min 60 -sc_threshold 0`은 30fps 기준 2초마다 키프레임을 고정한다. FFmpeg의 HLS 먹서는 `hls_time`이 지난 뒤 다음 키프레임에서 세그먼트를 자르므로, 키프레임 간격이 일정해야 세그먼트 길이가 고르게 나온다.
- `hls_time`의 기본값은 2초이므로 6초로 쓰려면 명시해야 한다.
- `hls_playlist_type vod`는 `EXT-X-PLAYLIST-TYPE:VOD`를 넣고, `independent_segments` 플래그는 모든 세그먼트가 키프레임으로 시작할 때 `EXT-X-INDEPENDENT-SEGMENTS`를 넣는다.
- 변형이 둘 이상이면 출력 경로에 `%v`가 있어야 한다.

비용은 처리량에 대한 가정이 필요하므로 이 단계에서 결론 내리지 않는다. 대신 같은 샘플 영상 묶음을 두 방식으로 처리해 **출력 1분당 비용**, **업로드 완료부터 재생 가능까지 걸린 시간**, **운영에 드는 작업량**을 비교하는 것을 1단계 과제로 둔다. 초기 트래픽이 작고 인코딩 경험이 적다면 MediaConvert로 시작하고, 처리량이 커져 단가가 문제가 될 때 FFmpeg로 옮기는 경로가 위험이 작다.

## 파이프라인과 CloudFront 전송

```text
클라이언트 ── 멀티파트 업로드 ──> S3 raw/
                                    │ (업로드 완료 API 또는 S3 이벤트)
                                    v
                              트랜스코딩 작업 생성
                         (MediaConvert 또는 Batch 작업)
                                    │
                                    v
                              S3 hls/<videoId>/v1/
                                    │ (완료 이벤트 → DB에 재생 URL 기록)
                                    v
             CloudFront (Origin Access Control로 S3 비공개 유지)
                                    │
                                    v
                         앱 플레이어 (master.m3u8)
```

전송 쪽 설계 결정은 다음과 같다.

- **버킷은 비공개로 두고 CloudFront만 읽게 한다.** OAC(Origin Access Control)로 CloudFront 배포에만 `s3:GetObject`를 허용한다.
- **경로에 버전을 넣는다.** VOD 플레이리스트와 세그먼트는 한 번 만들면 바뀌지 않으므로 긴 TTL로 캐시한다. 다시 인코딩해야 하면 덮어쓰지 않고 `v2/` 같은 새 경로에 만들고 재생 URL을 바꾼다. 캐시 무효화(invalidation)에 기대지 않는다.
- **접근 제어가 필요하면 서명된 쿠키를 검토한다.** HLS는 영상 하나가 플레이리스트 여러 개와 세그먼트 수십 개로 이루어지므로, 파일마다 서명된 URL을 만들기보다 서명된 쿠키(Signed Cookies)로 경로 단위 접근을 허용하는 편이 맞다. 공개 콘텐츠라면 서명 없이 시작한다.
- **웹 재생을 고려해 CORS를 연다.** 네이티브 플레이어는 CORS와 무관하지만, 웹에서 hls.js 같은 플레이어로 재생하려면 `.m3u8`과 세그먼트 응답에 CORS 헤더가 필요하다.

## 단계별 도입 계획

| 단계 | 범위 | 완료 조건 |
|---|---|---|
| 0. 기준선 측정 | 현재 MP4 재생의 지표 수집을 앱에 추가 | 아래 지표를 2주 이상 수집 |
| 1. 파이프라인 검증 | 샘플 영상으로 두 트랜스코딩 방식 비교, 사다리·세그먼트 길이 후보 결정 | 출력 1분당 비용, 처리 시간, 화질 비교표 |
| 2. 신규 업로드 이중 생성 | 새로 올라오는 영상에 대해 HLS를 추가 생성. 기존 MP4 재생은 유지 | 업로드 대비 HLS 생성 성공률과 처리 지연이 목표 이내 |
| 3. 점진적 재생 전환 | 기능 플래그로 일부 사용자만 HLS URL로 재생, MP4 그룹과 비교 | 기준선 대비 지표가 개선되거나 최소한 악화되지 않음 |
| 4. 확대와 백필 | 전체 사용자로 확대, 조회수가 높은 과거 영상부터 HLS 생성 | 롤백 없이 전체 전환 |
| 5. 정리 | MP4 사본의 보관 정책 결정(다운로드·공유용으로 남길지) | 저장 비용 재산정 |

HLS 생성이 실패하거나 아직 끝나지 않은 영상은 MP4로 재생하는 폴백(fallback)을 끝까지 유지한다. 재생 URL을 영상 단위로 내려 주는 API가 이미 있다면, 플래그와 폴백은 서버에서 URL을 고르는 로직만으로 구현할 수 있다.

## 무엇을 측정할 것인가

| 지표 | 정의 | 판단에 쓰는 이유 |
|---|---|---|
| 첫 프레임까지 시간(Time To First Frame) | 재생 요청부터 첫 프레임 표시까지 | 숏폼 체감 품질의 핵심 |
| 리버퍼링 비율(Rebuffering Ratio) | 재생 중 멈춘 시간 / 전체 재생 시간 | 적응형 스트리밍의 주된 목표 |
| 평균 재생 비트레이트와 전환 횟수 | 세션별 평균 변형, 변형이 바뀐 횟수 | 사다리 설계가 맞는지 확인 |
| 재생 오류율 | 재생 시작 실패, 중도 실패 비율 | 전환 단계의 안전 장치 |
| 시청 1분당 전송량 | CDN 전송 바이트 / 시청 시간 | 전송 비용 변화 |
| 인코딩 비용 | 출력 1분당 비용 | 트랜스코딩 방식 선택 근거 |
| 업로드 후 재생 가능까지 시간 | 업로드 완료 → HLS 준비 완료 | 업로드 직후 노출하는 서비스 특성상 중요 |

전송량은 줄어들 수도 늘어날 수도 있다. 저속 네트워크 사용자는 낮은 변형을 받아 줄어들지만, 빠른 네트워크 사용자는 기존보다 높은 품질로 올라가 늘어날 수 있다. 그래서 "HLS가 비용을 줄인다"를 전제로 두지 않고, 체감 품질 지표와 비용 지표를 함께 보고 결정한다.

## 정리

1. 단일 MP4 재생은 비트레이트가 하나뿐이라 네트워크 변화에 적응하지 못하고, 숏폼에서는 넘겨진 영상의 전송량도 낭비된다.
2. HLS는 마스터 플레이리스트(변형 목록)와 미디어 플레이리스트(세그먼트 목록)로 구성되며, Apple 사양은 `BANDWIDTH`, `AVERAGE-BANDWIDTH`, `CODECS`, `RESOLUTION`, `FRAME-RATE`를 요구한다.
3. 비트레이트 사다리는 Apple 예시를 세로 영상에 맞춰 3~4단계로 시작하고, 원본보다 높은 변형은 만들지 않으며 샘플 비교로 조정한다.
4. 세그먼트는 IDR로 시작하고 키프레임은 2초 간격으로 고정한 뒤, 권장 6초와 더 짧은 길이를 첫 프레임 시간 기준으로 비교한다.
5. 트랜스코딩은 관리형 MediaConvert와 직접 운영하는 FFmpeg를 비용·처리 시간·운영 부담으로 비교해 고르고, 작게 시작한다면 MediaConvert가 위험이 작다.
6. CloudFront는 OAC로 버킷을 숨기고, 버전 경로와 긴 TTL로 캐시하며, 도입은 기준선 측정 → 이중 생성 → 플래그 기반 점진 전환 순서로 진행한다.
