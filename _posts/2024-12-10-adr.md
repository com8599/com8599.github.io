코드는 무엇을 하는지는 보여 주지만, 왜 다른 방법이 아니라 이 방법을 골랐는지는 보여 주지 않는다. 메시지 큐 대신 DB 폴링을 쓴 이유, 세션 대신 토큰을 쓴 이유, 모놀리스를 나누지 않은 이유는 결정 당시 회의와 메신저에만 남고 시간이 지나면 사라진다. 그 결정을 내린 사람이 떠나면 남은 사람은 두 가지 중 하나를 고른다. 이유를 모른 채 그대로 따르거나, 이유를 모른 채 바꾼다. 아키텍처 결정 기록(Architecture Decision Record, ADR)은 이 공백을 메우기 위한 가벼운 문서 형식이다.

## 원형: Michael Nygard의 형식

ADR이라는 형식은 Michael Nygard가 2011년 11월 Cognitect 블로그의 글 "Documenting Architecture Decisions"에서 제안했다. 출발점이 된 문제의식은 이렇다. 새로 합류한 개발자가 이유가 기록되지 않은 과거 결정을 만나면 맹목적으로 받아들이거나(blind acceptance) 맹목적으로 뒤집을(blind reversal) 수밖에 없고, 둘 다 피해야 한다. 그리고 큰 문서는 갱신되지도 읽히지도 않으므로, 작고 모듈화된 문서여야 갱신될 가능성이라도 있다.

글이 제안한 형식은 다섯 부분으로 된다.

| 부분 | 내용 |
|---|---|
| 제목(Title) | 짧은 명사구. 예: "ADR 9: 멀티테넌트 연동에 LDAP 사용" |
| 맥락(Context) | 작용하는 힘(기술적, 정치적, 사회적, 프로젝트 고유의 제약). 서로 긴장 관계인 경우가 많다. 가치 판단 없이 사실로 기술한다 |
| 결정(Decision) | 그 힘에 대한 대응. 능동태 완전한 문장으로, "우리는 …한다(We will …)" 형태 |
| 상태(Status) | 제안됨(proposed), 승인됨(accepted), 이후 사용 중단(deprecated) 또는 대체됨(superseded) |
| 결과(Consequences) | 결정을 적용한 뒤의 상황. 긍정적인 것만이 아니라 부정적, 중립적 결과를 모두 적는다 |

분량은 한두 페이지로 하고, 미래의 개발자와 대화하듯 완전한 문장으로 쓴다. 글머리 기호는 시각적 배치에만 쓰고 문장을 대신하지 않는다. 한 ADR은 한 프로젝트의 중요한 결정 하나만 다루며, 한 ADR의 결과는 다음 ADR의 맥락이 되는 경우가 많다.

## 불변성과 대체

ADR의 가장 중요한 규칙은 **승인된 기록을 고쳐 쓰지 않는다**는 것이다. 번호는 순서대로 붙이고 재사용하지 않는다. 결정을 뒤집을 때도 이전 ADR을 지우지 않고 상태를 "대체됨"으로 바꾼 뒤 새 ADR을 가리키게 한다. Nygard는 그 결정이 한때 내려졌다는 사실 자체가 여전히 의미 있다고 설명한다.

```text
docs/adr/
  0001-record-architecture-decisions.md       상태: 승인됨
  0002-use-postgresql.md                      상태: 승인됨
  0003-poll-outbox-table-for-events.md        상태: 대체됨 (0007)
  0007-publish-events-via-sqs.md              상태: 승인됨, 0003을 대체
```

이렇게 남기면 현재 결정뿐 아니라 결정이 바뀐 경로가 보인다. "왜 처음에는 폴링이었나"라는 질문에 0003의 맥락이, "왜 바꿨나"라는 질문에 0007의 맥락이 답한다. 오탈자나 링크 수정 같은 편집은 허용하되, 결정 내용과 맥락을 바꾸는 수정은 새 ADR로 한다.

## 무엇을 기록하는가

Nygard는 기록 대상을 "아키텍처적으로 중요한" 결정, 즉 구조, 비기능적 특성, 의존성, 인터페이스, 구성 기법에 영향을 주는 결정으로 정의한다. 실무에서 판단하기 쉽게 바꾸면 다음과 같다.

| 기록한다 | 기록하지 않는다 |
|---|---|
| 되돌리는 비용이 큰 선택(DB, 메시지 브로커, 배포 방식) | 쉽게 되돌릴 수 있는 국소 구현 |
| 여러 팀이나 모듈에 영향을 주는 규약(API 버전 정책, 인증 방식) | 코딩 스타일처럼 린터가 강제하는 규칙 |
| 대안을 검토하고 하나를 고른 결정 | 선택지가 사실상 하나뿐이었던 결정 |
| 나중에 "왜 이렇게 했지?"라는 질문이 나올 것 같은 결정 | 티켓의 인수 조건으로 충분히 설명되는 기능 동작 |
| 의도적으로 하지 않기로 한 결정(지금은 마이크로서비스로 나누지 않는다) | 일정, 담당자 같은 계획 정보 |

"하지 않기로 한 결정"은 특히 기록할 가치가 크다. 코드에는 하지 않은 일의 흔적이 남지 않기 때문이다.

## 템플릿

Nygard 형식을 그대로 옮긴 최소 템플릿이다.

```text
# 7. 도메인 이벤트를 SQS로 발행한다

- 상태: 승인됨 (2024-12-03), 0003을 대체
- 결정자: 백엔드 팀

## 맥락
주문, 결제, 알림 모듈은 아웃박스 테이블을 5초 주기로 폴링해 이벤트를 처리한다(0003).
알림 발송 지연 요구가 1초 이내로 바뀌었고, 폴링 주기를 줄이면 DB 부하가 비례해 늘어난다.
운영 인원은 두 명이며 새로운 상태 저장 인프라를 직접 운영할 여력이 없다.

## 결정
아웃박스 테이블에 기록한 뒤 커밋 직후 SQS 표준 큐로 발행한다.
발행 실패분만 기존 폴러가 재시도한다. 소비자는 이벤트 ID로 멱등성을 보장한다.

## 결과
- 알림 지연이 폴링 주기에서 분리된다.
- 표준 큐는 순서를 보장하지 않으므로 순서가 필요한 소비자는 버전 필드로 판단해야 한다.
- AWS 서비스 의존이 하나 늘어나고, 로컬 개발에 큐 에뮬레이터가 필요하다.
```

### MADR

선택지 비교를 더 구조적으로 남기고 싶다면 MADR(Markdown Architectural Decision Records)을 쓴다. 2024년 9월 공개된 4.0.0의 구성은 다음과 같다.

| 섹션 | 필수 여부 |
|---|---|
| Context and Problem Statement | 필수 |
| Decision Drivers | 선택 |
| Considered Options | 필수 |
| Decision Outcome | 필수 |
| Consequences | 선택 |
| Confirmation(결정이 지켜지는지 확인하는 방법) | 선택 |
| Pros and Cons of the Options | 선택 |
| More Information | 선택 |

메타데이터는 YAML 앞부분에 `status`, `date`, `decision-makers`, `consulted`, `informed`를 둘 수 있다. 파일 이름은 `NNNN-title-with-dashes.md`, 기본 디렉터리는 `docs/decisions`다. Nygard 형식과 비교하면 검토한 대안과 각 대안의 장단점이 명시적인 섹션이 된다는 점이 가장 크다. 대안 비교가 중요한 결정이 많다면 MADR이, 가볍게 시작하고 싶다면 Nygard 형식이 맞다.

## 어디에 둘 것인가

| 위치 | 장점 | 단점 |
|---|---|---|
| 저장소의 `docs/adr`(또는 `docs/decisions`) | 코드와 같은 버전 관리, PR로 검토, 코드 변경과 같은 커밋에 묶을 수 있음 | 개발자가 아닌 사람이 찾기 어려움 |
| 위키 | 검색과 접근이 쉬움, 비개발자 참여 | 코드와 버전이 분리되고, 수정 이력이 덜 엄격함 |

Nygard는 프로젝트 저장소에 마크다운 같은 가벼운 텍스트 형식으로 두기를 제안했다. 결정이 영향을 주는 코드 바로 옆에 있어야 코드를 읽는 사람이 찾고, 결정이 바뀔 때 함께 갱신된다. 여러 저장소에 걸친 결정은 공통 저장소나 위키에 두고, 각 저장소의 ADR 목록에서 링크한다.

## 가벼운 검토 절차

ADR을 PR로 제출하면 별도의 승인 체계 없이 기존 코드 리뷰 흐름을 그대로 쓸 수 있다.

1. 작성자가 상태를 "제안됨"으로 둔 ADR을 PR로 연다. 관련 티켓 키를 제목에 넣는다.
2. 영향을 받는 사람을 리뷰어로 지정하고, 논의는 PR 코멘트에서 한다. 논의 결과로 맥락과 결과가 보강된다.
3. 합의되면 상태를 "승인됨"과 날짜로 바꾸고 병합한다. 기각된 제안은 원형 형식에 없는 "기각됨" 상태를 추가로 정의해 병합해 두는 것도 방법이다(MADR 등 이후 템플릿이 쓰는 관행). 같은 제안이 다시 나왔을 때 이전 논의를 찾을 수 있다.
4. 결정을 구현하는 PR은 ADR 번호를 본문에 링크한다.

검토 기간은 짧게 정한다. ADR은 완벽한 설계 문서가 아니라 결정 시점의 맥락을 남기는 기록이므로, 오래 붙잡고 있으면 결정 자체가 늦어진다.

## 온보딩 효과

새로 합류한 개발자가 코드베이스에서 가장 많이 묻는 것은 "이건 왜 이렇게 되어 있나요?"다. ADR 목록을 번호순으로 읽으면 시스템이 어떤 제약에서 출발해 어떤 경로로 지금 모습이 되었는지를 따라갈 수 있다. 질문에 답하는 사람의 시간이 줄어들 뿐 아니라, 답하는 사람이 기억에 의존해 재구성한 이유가 아니라 결정 당시의 이유를 전달할 수 있다. Nygard도 같은 글에서 ADR을 읽은 개발자들이 전달받은 맥락을 높이 평가했다고 적었다.

## 다른 기록 수단과의 비교

| 항목 | ADR | 설계 문서(Design Doc) | 위키 페이지 | PR 설명 |
|---|---|---|---|---|
| 목적 | 결정 하나와 그 이유 | 구현 전 설계 전체 검토 | 현재 상태 안내 | 변경 하나의 설명 |
| 분량 | 한두 페이지 | 수 페이지 이상 | 제한 없음 | 짧음 |
| 시점 | 결정 시점 | 구현 착수 전 | 수시 | 변경 시점 |
| 수정 | 불변, 대체로 갱신 | 검토 중 수정, 이후 잘 갱신되지 않음 | 계속 덮어씀 | 병합 후 고정 |
| 찾는 경로 | 저장소 목록, 번호 | 문서 저장소 | 검색 | blame → 커밋 → PR |
| 약점 | 큰 설계의 세부는 담기 어려움 | 낡아도 표시되지 않음 | 과거 결정의 이유가 덮어써짐 | 여러 PR에 걸친 결정은 흩어짐 |

설계 문서와 ADR은 경쟁하지 않는다. 설계 문서의 검토 과정에서 나온 핵심 결정을 ADR로 뽑아 남기면, 설계 문서가 낡더라도 결정과 이유는 남는다.

## 정리

1. ADR은 Michael Nygard가 2011년에 제안한 짧은 결정 기록으로, 제목, 맥락, 결정, 상태, 결과로 구성된다.
2. 맥락은 가치 판단 없이 사실로, 결정은 능동태 문장으로, 결과는 부정적인 것까지 모두 적는다.
3. 승인된 ADR은 고쳐 쓰지 않고, 바뀐 결정은 새 ADR로 남기고 이전 것을 "대체됨"으로 표시한다.
4. 되돌리기 비싼 결정, 여러 모듈에 걸친 규약, 하지 않기로 한 결정을 기록한다.
5. 대안 비교를 구조화하려면 MADR을 쓰고, 저장 위치는 코드와 함께 버전 관리되는 저장소를 기본으로 한다.
6. ADR을 PR로 검토하면 별도 절차 없이 합의 과정까지 남고, 번호순으로 읽는 목록이 그대로 온보딩 자료가 된다.
