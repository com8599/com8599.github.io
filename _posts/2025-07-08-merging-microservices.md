마이크로서비스(Microservices)의 약속은 독립 배포다. 한 서비스를 바꾸고 배포할 때 다른 서비스를 건드리지 않아도 되고, 한 서비스의 장애가 다른 서비스로 번지지 않는다. 그런데 서비스를 너무 잘게 나누면 정반대 상황이 된다. 프로세스는 여러 개인데 배포는 함께 해야 하고, 한 요청이 서비스 다섯 개를 거치며, 그중 하나만 느려도 전체가 느려진다. 이런 상태를 흔히 분산 모놀리스(Distributed Monolith)라고 부른다. 모놀리스의 결합은 그대로 두고 네트워크 비용과 운영 비용만 더한 구조다.

이 글은 분산 모놀리스를 알아보는 증상, 서비스 경계를 판단하는 기준, 그리고 경계가 잘못 그어진 서비스를 NestJS 모듈러 모놀리스(Modular Monolith)로 합치는 단계를 정리한다.

## 증상

| 증상 | 관찰 방법 | 의미 |
|---|---|---|
| 수다스러운 동기 호출(Chatty calls) | 요청 하나당 서비스 간 HTTP 호출 수, 트레이스의 호출 깊이 | 하나의 일을 여러 서비스가 나눠 하고 있다 |
| 동시 배포(Lockstep deploy) | 한 기능 PR이 여러 저장소에 걸치는 빈도, 같은 날 함께 나가는 배포 | 계약이 자주 함께 바뀐다. 독립 배포가 안 된다 |
| 공유 데이터베이스 | 여러 서비스가 같은 테이블을 읽고 쓴다 | 스키마 변경이 모든 서비스에 영향을 준다 |
| 연쇄 장애 | 한 서비스 장애 때 함께 오류율이 오르는 서비스 수 | 동기 의존이 장애 경로가 된다 |
| 분산 트랜잭션 보상 코드 | 사가(Saga), 보상 API, 재처리 배치의 양 | 한 트랜잭션이어야 할 일이 서비스 경계에 잘렸다 |
| 서비스 수 > 운영 역량 | 담당자 없는 서비스, 오래 배포되지 않은 서비스 | 나눈 비용을 감당할 조직이 없다 |

증상 하나만으로 판단하지 않는다. 결제와 주문처럼 호출이 많아도 경계가 맞는 경우가 있다. 여러 증상이 **같은 서비스 쌍에서 겹쳐** 나타날 때 합칠 후보로 본다.

## 결합도와 응집도

서비스 경계의 품질은 결국 결합도(Coupling)와 응집도(Cohesion)의 문제다.

- **응집도**: 함께 바뀌는 것들이 한 곳에 모여 있는 정도. 요구사항 하나가 서비스 하나 안에서 끝나면 응집도가 높다.
- **결합도**: 한쪽을 바꿀 때 다른 쪽도 바꿔야 하는 정도. 서비스 사이에서는 API 계약, 공유 스키마, 호출 순서에 대한 가정이 결합을 만든다.

마이크로서비스는 응집도가 높은 단위로 나눴을 때만 이득이 있다. 응집된 단위를 둘로 쪼개면 내부 함수 호출이 네트워크 호출로, 로컬 트랜잭션이 분산 트랜잭션으로, 리팩터링이 API 버전 관리로 바뀐다. Martin Fowler는 MonolithFirst(2015)에서 "서비스 사이에서 기능을 옮기는 리팩터링은 모놀리스 안에서보다 훨씬 어렵다"고 지적하고, 경험 많은 아키텍트도 처음부터 경계를 정확히 긋기 어렵다고 말한다.

변경 결합은 코드보다 이력에서 잘 보인다. 최근 몇 달간 기능 PR이 어느 저장소들에 함께 걸쳤는지, 같은 티켓 키로 여러 서비스에 커밋이 남았는지를 세어 보면, 사실상 한 덩어리로 움직이는 서비스 묶음이 드러난다.

## 경계 기준 1: 바운디드 컨텍스트

도메인 주도 설계(Domain-Driven Design, DDD)의 바운디드 컨텍스트(Bounded Context)는 하나의 모델과 용어가 일관되게 통하는 범위다. 큰 시스템 전체에 단일 모델을 강제하는 대신, 컨텍스트별로 모델을 따로 두고 컨텍스트 사이의 관계를 명시한다.

서비스 경계를 판단할 때 유용한 질문은 다음과 같다.

- 같은 단어가 같은 뜻인가? "주문"이 주문 서비스와 배송 서비스에서 다른 속성과 생명주기를 가진다면 별도 컨텍스트일 가능성이 크다.
- 하나의 불변식(Invariant)을 지키는 데 두 서비스의 데이터가 모두 필요한가? "재고가 없으면 주문할 수 없다"를 한 트랜잭션으로 지켜야 한다면, 그 두 데이터는 같은 경계 안에 있어야 한다.
- 한 서비스가 다른 서비스의 데이터를 거의 그대로 복제해 들고 있는가? 복제가 아니라 같은 모델을 나눠 가진 것일 수 있다.

잘게 나뉜 서비스는 대개 **한 컨텍스트를 기술 계층이나 엔티티 단위로 자른 결과**다. "주문 생성 서비스", "주문 조회 서비스", "주문 상태 서비스"처럼 같은 모델을 다루는 서비스들은 하나의 컨텍스트로 합치는 것이 자연스럽다.

## 경계 기준 2: 콘웨이 법칙과 팀 규모

Melvin Conway는 1968년 Datamation에 실린 "How Do Committees Invent?"에서 시스템을 설계하는 조직은 그 조직의 커뮤니케이션 구조를 복제한 설계를 만들게 된다고 썼다. 이것이 콘웨이 법칙(Conway's Law)이다. James Lewis와 Martin Fowler의 "Microservices"(2014)는 이를 근거로 서비스를 비즈니스 역량(Business Capability) 단위로 나누고, 그 역량을 한 팀이 끝까지 맡는 구성을 설명한다. 같은 글에서 팀 규모의 예로 Amazon의 "피자 두 판 팀(Two Pizza Team)", 대략 열두 명 이하를 든다.

여기서 나오는 실무적 기준은 다음과 같다(공식 규칙이 아니라 경험칙이다).

| 상황 | 해석 |
|---|---|
| 한 팀이 서비스 여러 개를 맡고, 그 서비스들이 늘 함께 바뀐다 | 조직 경계와 서비스 경계가 어긋남. 합칠 후보 |
| 서비스 하나를 여러 팀이 함께 고친다 | 서비스가 너무 크거나 소유권이 불분명함. 나눌 후보 |
| 팀 수에 비해 서비스 수가 훨씬 많다 | 배포·모니터링·온콜 부담이 사람 수를 넘음 |

Fowler의 MicroservicePrerequisites(2014)는 마이크로서비스의 전제 조건으로 빠른 프로비저닝, 기본 모니터링, 빠른 배포, 개발·운영 협업 문화를 든다. 서비스 수가 이 역량을 넘어서면 나눈 이점보다 운영 비용이 커진다.

## 합칠 목표: 모듈러 모놀리스

합친다고 해서 경계를 없애는 것은 아니다. 목표는 **배포 단위는 하나, 내부 경계는 명확한** 모듈러 모놀리스다. NestJS에서는 이전 서비스 하나가 모듈 하나가 된다.

| 항목 | 분산 모놀리스 | 모듈러 모놀리스 |
|---|---|---|
| 배포 단위 | 서비스 여러 개(실제로는 함께 배포) | 하나 |
| 모듈 간 호출 | HTTP/메시지, 타임아웃·재시도 필요 | 프로세스 내 함수 호출 |
| 트랜잭션 | 분산 트랜잭션, 보상 로직 | 필요한 곳은 로컬 트랜잭션 |
| 경계 강제 | 네트워크가 강제(대신 비쌈) | 모듈 공개 API와 린트 규칙으로 강제 |
| 다시 분리 | 이미 분리됨 | 경계가 지켜졌다면 모듈 단위로 분리 가능 |

경계를 지키는 장치는 세 가지다.

1. **모듈의 공개 API**: 모듈은 `exports`에 올린 서비스(또는 인터페이스 토큰)만 노출한다. 다른 모듈의 리포지토리나 엔티티를 직접 주입하지 않는다.
2. **데이터 소유권**: 테이블마다 소유 모듈을 정하고, 다른 모듈의 테이블을 직접 조인하거나 쓰지 않는다. 필요하면 소유 모듈의 공개 메서드를 부른다.
3. **import 규칙**: ESLint의 `no-restricted-imports` 등으로 다른 모듈의 내부 경로(`orders/internal/*`) import를 막는다.

## 합치는 단계

### 1. 호출과 데이터 지도 그리기

분산 트레이싱이나 게이트웨이 로그로 서비스 간 호출 관계와 빈도를 뽑고, 서비스별로 읽고 쓰는 테이블을 정리한다. 이 지도에서 호출이 많고, 함께 배포되고, 같은 데이터를 만지는 서비스 묶음을 고른다.

### 2. 한 저장소, 한 프로세스로 모으기

코드를 한 저장소로 모은다. NestJS라면 [Nest CLI 모노레포 모드](/2025/06/17/nestjs-monorepo/)로 각 서비스를 앱으로 들여온 뒤, 합칠 앱들의 모듈을 하나의 앱에 import하는 순서가 안전하다. 이 단계에서는 아직 모듈 사이 호출이 HTTP 그대로다.

### 3. 원격 호출을 인터페이스 뒤로 숨기고 구현만 바꾸기

호출하는 쪽이 HTTP 클라이언트를 직접 쓰고 있었다면, 먼저 인터페이스(포트)를 만들고 HTTP 구현을 그 뒤로 옮긴다. 그다음 같은 인터페이스의 프로세스 내 구현으로 교체한다. 호출하는 쪽 코드는 바뀌지 않는다.

```typescript
// inventory/inventory.port.ts
export const INVENTORY_PORT = Symbol('INVENTORY_PORT');

export interface InventoryPort {
  reserve(orderId: string, items: { sku: string; qty: number }[]): Promise<string>;
}
```

```typescript
// 합치기 전: 원격 서비스를 부르는 구현
@Injectable()
export class HttpInventoryAdapter implements InventoryPort {
  constructor(private readonly http: HttpService) {}

  async reserve(orderId: string, items: { sku: string; qty: number }[]) {
    const res = await firstValueFrom(
      this.http.post<{ reservationId: string }>('/reservations', { orderId, items }),
    );
    return res.data.reservationId;
  }
}

// 합친 뒤: 같은 프로세스의 모듈을 부르는 구현
@Injectable()
export class LocalInventoryAdapter implements InventoryPort {
  constructor(private readonly reservations: ReservationService) {}

  reserve(orderId: string, items: { sku: string; qty: number }[]) {
    return this.reservations.reserve(orderId, items);
  }
}
```

```typescript
// orders/orders.module.ts
@Module({
  imports: [InventoryModule], // ReservationService를 exports하는 모듈
  providers: [
    OrdersService,
    { provide: INVENTORY_PORT, useClass: LocalInventoryAdapter },
  ],
})
export class OrdersModule {}
```

`OrdersService`는 `@Inject(INVENTORY_PORT)`로 포트만 알고 있으므로 구현 교체가 한 줄로 끝난다. 인터페이스를 남겨 두는 이유는 나중에 이 경계를 다시 서비스로 분리할 수 있게 하기 위해서다. provider 교체와 토큰 주입 방식은 [NestJS 모듈 캡슐화와 의존성 주입](/2022/07/27/nestjs-module-di/)을 참고한다.

프로세스 내 호출로 바꾸면 의미가 달라지는 부분도 있다. 원격 호출에 있던 타임아웃·재시도·직렬화가 사라지고, 예외가 그대로 호출자에게 전파된다. 원격 오류 코드를 해석하던 분기는 정리하고, 직렬화 과정에서 암묵적으로 일어나던 변환(Date가 문자열이 되는 등)에 기대던 코드가 없는지 확인한다.

### 4. 데이터 합치기

데이터베이스는 코드보다 나중에, 더 천천히 합친다.

| 단계 | 내용 |
|---|---|
| 같은 DB 서버, 다른 스키마 | 물리적으로 모으되 테이블 소유권은 그대로 둔다 |
| 소유 모듈만 쓰기 | 다른 모듈 테이블에 대한 쓰기 경로를 모두 공개 메서드 호출로 바꾼다 |
| 로컬 트랜잭션 도입 | 불변식을 함께 지켜야 하는 쓰기만 하나의 트랜잭션으로 묶는다 |
| 보상 로직 제거 | 로컬 트랜잭션으로 대체된 사가·보상 API·재처리 배치를 걷어낸다 |

모듈을 넘나드는 트랜잭션은 편하지만 경계를 흐린다. 불변식 때문에 꼭 필요한 곳에만 쓰고, 나머지는 기존처럼 이벤트나 비동기 처리로 남겨 둔다.

### 5. 외부 경로 유지와 이전 서비스 제거

클라이언트가 부르던 공개 경로는 합친 뒤에도 그대로 유지하고, 게이트웨이에서 새 프로세스로 라우팅만 바꾼다(게이트웨이 라우팅은 별도 글에서 다룬다). 트래픽이 모두 옮겨지면 이전 서비스의 배포 파이프라인, 모니터링, 알림, DNS를 함께 정리한다.

## 정리

1. 분산 모놀리스는 서비스는 나뉘었지만 배포·장애·데이터가 함께 묶인 상태다. 수다스러운 호출, 동시 배포, 공유 DB가 같은 서비스 쌍에서 겹치면 합칠 후보다.
2. 경계는 응집도가 높은 단위, 즉 바운디드 컨텍스트를 따라 긋는다. 하나의 불변식을 지키는 데이터는 같은 경계 안에 둔다.
3. 콘웨이 법칙에 따라 서비스 경계는 팀 경계와 맞아야 하며, 서비스 수는 운영 역량 안에 있어야 한다.
4. 합칠 목표는 모듈러 모놀리스다. 모듈 공개 API, 데이터 소유권, import 규칙으로 내부 경계를 유지한다.
5. 원격 호출은 인터페이스 뒤로 옮긴 뒤 프로세스 내 구현으로 교체하고, 데이터는 소유권을 유지한 채 단계적으로 합친다.
