작은 팀은 기획서, 회의록, 태스크를 한 도구에 모으는 경우가 많다. 노션(Notion) 같은 위키형 도구는 문서와 데이터베이스가 같은 공간에 있어서, 따로 이슈 트래커를 두는 것보다 시작 비용이 낮다. 문제는 자유도가 높다는 점이다. 같은 정보가 문서 본문, 태스크 카드, 메신저에 흩어지고, 상태 값의 의미가 사람마다 달라지면 보드는 금방 현실과 어긋난다.

이 글은 위키형 도구로 태스크를 관리할 때 지켜야 할 최소 규칙을 원리 위주로 정리한다. 티켓 본문 작성법과 완료 정의는 [티켓 작성 규칙](/2022/01/05/ticket-conventions/)에서, 담당자 공백과 대기 시간은 [방치되는 티켓 줄이기](/2022/04/26/ticket-aging-escalation/)에서 다뤘다.

## 단일 진실 공급원(Single Source of Truth)

단일 진실 공급원은 어떤 정보에 대해 **원본이 한 곳에만 있고, 나머지는 그 원본을 참조한다**는 원칙이다. 일감 관리에서 이 원칙이 깨지는 전형적인 경로는 복사다.

- 기획서의 요구사항을 태스크 본문에 붙여 넣는다.
- 기획서가 바뀐다. 태스크 본문은 그대로다.
- 개발자는 태스크를 보고 구현하고, 리뷰어는 기획서를 보고 리뷰한다.

두 사람이 서로 다른 버전을 보고 있으니 리뷰에서 "그게 아니다"가 나오고, 재작업이 생긴다. 복사본은 만든 순간부터 낡기 시작한다. 그래서 정보마다 원본 위치를 정해 둔다.

| 정보 | 원본 위치 | 다른 곳에서는 |
|---|---|---|
| 요구사항, 화면 정의 | 기획 문서(스펙) | 태스크에서 관계로 연결 |
| 할 일, 담당자, 상태, 기한 | 태스크 데이터베이스 | 문서에는 태스크 목록 뷰를 삽입 |
| 구현 세부, 코드 변경 | 저장소(PR, 커밋) | 태스크에는 PR 링크만 |
| 결정과 그 이유 | 결정 기록 | 태스크와 문서에서 링크 |

결정 기록을 어디에 둘지는 [ADR 글](/2024/12/10/adr/)에서 따로 다뤘다.

## 복사 대신 관계(Relation)로 연결한다

노션 데이터베이스의 관계(Relation) 속성은 서로 다른 데이터베이스의 페이지를 연결한다. 두 데이터베이스 사이의 관계는 기본이 단방향이고, 양방향으로 켜면 상대 데이터베이스에도 대응 속성이 생겨 양쪽에서 함께 갱신된다. 관계 대상 수는 "1페이지"로 제한하거나 제한 없이 둘 수 있다.

관계를 쓰면 다음이 가능해진다.

- 스펙 페이지에서 "이 스펙에 딸린 태스크"가 자동으로 보인다.
- 롤업(Rollup)으로 관련 페이지의 값을 집계한다. 개수 세기, 빈 값/비지 않은 값의 비율, 숫자 합계·평균, 날짜의 최초·최종 값 같은 계산을 지원한다. 예를 들어 스펙마다 "연결된 태스크 중 완료 비율"을 표시할 수 있다.
- 스펙이 바뀌면 원본 한 곳만 고치면 되고, 태스크는 항상 최신 스펙을 가리킨다.

롤업은 다시 롤업할 수 없다(순환 가능성 때문). 데이터베이스를 복제하면 양방향 관계가 단방향으로 바뀌고, CSV로 내보내면 관계는 URL 텍스트로만 남는다. 관계를 많이 쓸수록 이 도구 밖으로 옮기기는 어려워진다는 뜻이다.

## 상태는 공유 어휘다

상태 값은 보드의 열 이름이 아니라 **팀이 합의한 정의**다. "진행 중"이 누구에게는 "생각해 보는 중"이고 누구에게는 "PR을 올린 상태"라면, 보드를 보고 내린 판단은 전부 틀린다.

노션의 상태(Status) 속성은 상태 값들을 할 일(To-do), 진행 중(In progress), 완료(Complete)의 세 그룹으로 묶는다. 그룹 안에 값을 몇 개 둘지는 팀이 정하지만, 값마다 **진입 조건**을 한 줄로 적어 두지 않으면 공유 어휘가 되지 않는다.

| 상태 | 그룹 | 진입 조건 |
|---|---|---|
| 대기 | 할 일 | 스펙이 연결되어 있고 담당자가 정해짐 |
| 진행 중 | 진행 중 | 담당자가 착수함(브랜치 생성 또는 첫 커밋) |
| 리뷰 | 진행 중 | PR이 열리고 리뷰어가 지정됨 |
| 막힘 | 진행 중 | 외부 답변·의존 작업 대기. 사유를 본문 첫 줄에 적음 |
| 완료 | 완료 | PR 병합 및 완료 정의 충족 |

상태 수는 적을수록 지키기 쉽다. 진입 조건을 한 문장으로 설명할 수 없는 상태는 합치거나 없앤다.

## 태스크당 담당자는 한 명

담당자(Person) 속성에 여러 명을 넣을 수 있다고 해서 넣으면 안 된다. 담당자가 둘이면 각자 상대가 하고 있다고 가정한다. 담당자는 "작업을 혼자 하는 사람"이 아니라 **상태를 갱신하고 막힘을 알릴 책임자**다. 협업자가 필요하면 별도의 "참여자" 속성을 둔다. 담당자 속성 하나를 기준으로 쓰면 "내 태스크" 뷰와 담당자 기반 권한 규칙도 단순해진다.

## 뷰는 같은 데이터를 보는 다른 렌즈다

노션은 하나의 데이터베이스를 표, 보드, 타임라인, 캘린더, 리스트, 갤러리 같은 여러 뷰로 볼 수 있고, 필터·정렬·그룹은 뷰마다 따로 저장된다. 원리는 SQL의 뷰와 같다. **데이터는 하나, 질의가 여러 개**다.

| 뷰 | 레이아웃 | 필터/그룹 | 보는 사람 |
|---|---|---|---|
| 내 태스크 | 리스트 | 담당자 = 나, 상태 ≠ 완료 | 개발자 |
| 진행 보드 | 보드 | 상태별 그룹, 현재 주기 | 팀 전체(스탠드업) |
| 출시 일정 | 타임라인 | 마일스톤별 그룹 | 기획, 리드 |
| 정리 대상 | 표 | 담당자 없음 또는 오래 수정 안 됨 | 리드 |

흔한 실수는 팀이나 프로젝트마다 **데이터베이스를 새로 만드는 것**이다. 데이터베이스가 둘이면 "전체에서 담당자 없는 태스크"를 한 번에 볼 수 없고, 상태 정의도 따로 놀기 시작한다. 구분이 필요하면 속성(팀, 프로젝트)을 추가하고 뷰로 나눈다.

## 최소 속성 스키마

속성이 많을수록 입력을 건너뛰는 사람이 늘어난다. 필수 속성은 아래 정도로 충분하다.

| 속성 | 타입 | 필수 | 용도 |
|---|---|---|---|
| 제목 | 제목(Title) | 예 | 동사로 시작하는 결과 중심 문장 |
| ID | 고유 ID(Unique ID) | 자동 | `TASK-123` 형식. 브랜치·PR에서 참조 |
| 상태 | 상태(Status) | 예 | 위의 다섯 값 |
| 담당자 | 사람(Person) | 예 | 한 명 |
| 스펙 | 관계(Relation) → 스펙 DB | 기능 태스크는 예 | 요구사항 원본 |
| 유형 | 선택(Select) | 예 | 기능 / 버그 / 작업 |
| 우선순위 | 선택(Select) | 예 | 높음 / 보통 / 낮음 |
| 주기 또는 마일스톤 | 관계 또는 선택 | 아니요 | 계획 단위 |
| PR | GitHub Pull Requests | 자동 | PR 연결과 상태 동기화 |
| 생성자, 최종 편집 시각 | 생성자(Created by), 최종 편집 일시(Last edited time) | 자동 | 정리 기준 |

고유 ID는 새 항목과 기존 항목 모두에 자동으로 붙고 번호는 바뀌지 않는다. 접두사는 나중에 바꿀 수 있다. 이 ID가 코드와 태스크를 잇는 키가 된다. 키를 브랜치와 커밋에 남기는 이유는 [추적성 글](/2024/08/27/traceability/)에서 다뤘다.

규칙 위반을 눈으로 찾지 않도록 수식(Formula) 속성으로 경고를 만들어 둔다.

```javascript
if(
  prop("상태") == "진행 중" and dateBetween(now(), prop("최종 편집 일시"), "days") > 3,
  "3일 이상 갱신 없음",
  if(empty(prop("담당자")) and prop("상태") != "완료", "담당자 없음", "")
)
```

수식 결과가 비어 있지 않은 항목만 필터링하면 "정리 대상" 뷰가 된다. 담당자 없이 진행 중인 태스크를 API로 점검할 때의 필터 본문은 다음과 같다.

```json
{
  "filter": {
    "and": [
      { "property": "상태", "status": { "equals": "진행 중" } },
      { "property": "담당자", "people": { "is_empty": true } }
    ]
  }
}
```

## 위키형 도구에 부족한 것

데이터베이스로 태스크 목록은 만들 수 있지만, 이슈 트래커가 기본으로 갖춘 것 중 일부는 약하거나 없다. 부족한 부분은 대개 **개발 흐름의 자동화**에서 드러난다.

| 영역 | 노션 데이터베이스(2025년 10월 기준) | 전용 이슈 트래커 일반 | 개발 흐름에 주는 영향 |
|---|---|---|---|
| 코드 연동 | GitHub 연동으로 PR 연결, PR 상태에 따른 태스크 상태 자동 변경, PR·이슈의 동기화 데이터베이스(읽기 전용) | 브랜치·커밋·PR·배포까지 이슈에 모아 보여 주는 개발 패널 | 연동이 얕을수록 상태 갱신을 사람이 해야 하고, 보드가 늦게 따라온다 |
| 자동화 | 데이터베이스 자동화(페이지 추가, 속성 변경, 반복 일정 트리거). 유료 요금제 필요, 무료는 Slack 알림만 | 워크플로 전이 규칙, 전이 조건 검사 | 무료 요금제에서는 상태 기반 자동 배정·알림을 만들 수 없다 |
| 상태 전이 강제 | 상태 값은 자유롭게 바꿀 수 있다 | 허용된 전이만 가능하게 제한하거나 필수 필드를 요구할 수 있다 | "대기 → 완료" 같은 건너뛰기를 막지 못하므로 규칙은 합의로 지킨다 |
| 권한 | 데이터베이스의 "콘텐츠 편집 가능" 권한, 사람 속성 기반 페이지 단위 규칙 | 프로젝트·역할별 권한 체계 | 외부 협력자에게 일부만 보여 주기는 가능하나 세밀하지 않다 |
| 이력 | 페이지 기록. 보존 기간이 요금제별(무료 7일, Plus 30일, Business 90일, Enterprise 무제한) | 필드 단위 변경 이력이 영구 보존 | 상태별 체류 시간 같은 흐름 지표를 사후에 계산하기 어렵다 |

마지막 줄이 특히 중요하다. 리드 타임, 상태별 체류 시간 같은 흐름 지표는 **상태가 언제 바뀌었는지**의 이력이 있어야 계산할 수 있다. 위키형 도구에서는 이 이력이 페이지 기록 안에 섞여 있고 보존 기간도 짧으므로, 지표가 필요하면 "착수일", "완료일" 날짜 속성을 따로 두고 자동화로 채우는 식으로 보완한다.

### GitHub 연동이 해 주는 것

노션의 GitHub Pull Requests 속성은 접두사가 있는 고유 ID 속성을 전제로 한다. PR 설명에 매직 워드와 태스크 ID를 쓰면 연결된다.

```text
fixes TASK-128
related to TASK-131
```

닫기 계열 단어(`close`, `fix`, `resolve`, `complete` 등)로 연결한 태스크는 PR이 병합되면 완료로 표시되고, 참조 계열 단어(`ref`, `related to`, `part of` 등)로 연결한 태스크는 완료 처리되지 않는다. 속성의 자동 갱신(Auto-update) 설정에서는 PR이 열림(Opened), 리뷰 요청(Review Requested), 승인(Approved), 병합(Merged)될 때 각각 어떤 상태로 바꿀지 지정할 수 있다. 이 설정을 쓰면 "리뷰", "완료" 상태를 사람이 옮길 필요가 없어진다. 노션 워크스페이스는 GitHub 조직 하나에만 연결할 수 있고, 연결하려면 노션 워크스페이스 소유자이면서 GitHub 조직 관리자여야 한다.

## 전용 트래커로 옮길 시점

위키형 도구는 "문서와 일감이 붙어 있다"는 장점으로 시작 비용을 낮춘다. 그 장점보다 위 표의 부족한 점이 더 비싸지는 순간이 옮길 시점이다. 아래는 공식 기준이 아니라 경험칙이다.

| 신호 | 의미 |
|---|---|
| 상태 갱신이 늦어 스탠드업에서 보드를 먼저 고친다 | 코드 이벤트로 상태를 바꾸는 연동이 부족하다 |
| 리드 타임, 상태별 체류 시간을 측정해야 한다 | 상태 전이 이력이 필요하다 |
| 상태 건너뛰기, 필수 값 누락이 반복된다 | 전이 규칙 강제가 필요하다 |
| 개발 외 조직(CS, QA)이 이슈를 대량으로 등록한다 | 접수 양식, 권한, 분류 자동화가 필요하다 |
| 태스크 데이터베이스가 여러 개로 갈라졌다 | 하나의 스키마를 강제할 도구가 필요하다 |

옮기더라도 문서는 위키에 남기고, 일감만 트래커로 옮긴 뒤 서로 링크하는 구성이 흔하다. 단일 진실 공급원 원칙은 그대로다. 요구사항의 원본은 문서, 일감 상태의 원본은 트래커다.

## 정리

1. 정보마다 원본 위치를 하나로 정하고, 다른 곳에서는 복사하지 않고 참조한다. 복사본은 만든 순간부터 낡는다.
2. 스펙과 태스크는 관계 속성으로 연결하고, 진행률 같은 파생 값은 롤업으로 계산한다.
3. 상태 값마다 진입 조건을 한 줄로 정의해 공유 어휘로 만들고, 상태 수는 최소로 둔다.
4. 태스크당 담당자는 한 명이며, 담당자는 상태 갱신과 막힘 보고의 책임자다.
5. 데이터베이스는 하나로 두고 팀·프로젝트별 구분은 속성과 뷰로 한다. 뷰는 같은 데이터에 대한 다른 질의다.
6. 위키형 도구는 코드 연동, 전이 강제, 변경 이력이 약하다. 흐름 지표와 자동화가 필요해지면 일감만 전용 트래커로 옮기고 문서는 남긴다.
