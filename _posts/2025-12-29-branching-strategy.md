브랜치 전략은 "브랜치 이름을 어떻게 짓는가"의 문제가 아니라 **변경이 얼마나 자주, 얼마나 큰 단위로 합쳐지는가**를 정하는 규칙이다. 통합 빈도가 정해지면 충돌의 크기, 리뷰 대기, 배포 주기가 따라 정해진다. 이 글은 대표적인 세 모델을 원문 기준으로 정리하고, 앱 스토어 심사가 끼어 있는 모바일 앱과 언제든 배포할 수 있는 백엔드를 함께 운영하는 작은 팀에서 무엇을 고를지 다룬다.

작업을 작게 쪼개는 이유와 DORA 지표의 관계는 [일감 크기와 리드 타임](/2024/03/19/ticket-size-lead-time/)에서, 브랜치 이름과 커밋에 티켓 키를 남기는 규칙은 [추적성](/2024/08/27/traceability/)에서 다뤘다.

## 통합은 미룰수록 비싸진다

브랜치를 따로 두면 그동안 두 줄기의 코드가 서로를 모른 채 바뀐다. 합칠 때 드러나는 충돌은 두 종류다.

- **텍스트 충돌**: 같은 줄을 양쪽에서 고쳤다. Git이 알려 준다.
- **의미 충돌(Semantic Conflict)**: 줄은 겹치지 않지만 한쪽이 바꾼 함수 시그니처나 가정을 다른 쪽이 그대로 쓴다. Git은 깨끗하게 병합하고, 빌드나 런타임에서야 드러난다.

Martin Fowler는 브랜칭 패턴 글에서 큰 병합의 문제는 작업량 자체보다 그 작업의 **불확실성**이라고 하고, 잦은 통합은 병합 횟수를 늘리지만 각 병합의 복잡도와 위험을 줄인다고 정리한다. 작은 병합은 기하급수적으로(exponentially) 쉽다는 표현도 쓴다.

그래서 브랜치 전략을 평가하는 첫 질문은 "브랜치가 몇 종류인가"가 아니라 **"작업 브랜치가 메인 줄기와 얼마나 오래 떨어져 있는가"**다. 오래 사는 브랜치(Long-lived Branch)는 그 기간만큼 의미 충돌을 쌓고, 리뷰할 diff를 키우고, 다른 사람이 그 위에 작업을 얹게 만든다.

## Git Flow

Vincent Driessen이 2010년 1월 "A successful Git branching model"에서 제안한 모델이다. 두 개의 영구 브랜치와 세 종류의 보조 브랜치로 이루어진다.

| 브랜치 | 분기 지점 | 병합 대상 | 역할 |
|---|---|---|---|
| `master` | — | — | 운영 배포 가능한 코드. 병합마다 새 릴리스이며 버전 태그를 단다 |
| `develop` | — | — | 다음 릴리스를 위한 통합 브랜치 |
| `feature/*` | `develop` | `develop` | 기능 개발 |
| `release-*` | `develop` | `master`, `develop` | 릴리스 준비. 시작할 때 버전 번호를 정하고, 큰 기능은 넣지 않는다 |
| `hotfix-*` | `master` | `master`, `develop` | 운영 긴급 수정. 릴리스 브랜치가 살아 있으면 `develop` 대신 그쪽으로 병합 |

원문은 병합에 `--no-ff`를 쓰라고 권한다. 빨리 감기(Fast-forward)가 가능해도 병합 커밋을 만들어, 기능 브랜치가 있었다는 사실과 그 기능의 커밋 묶음을 이력에 남기고 기능 전체를 되돌리기 쉽게 하려는 것이다.

```bash
# 릴리스 준비: develop에서 분기해 버전만 올리고 안정화
git switch -c release-1.4.0 develop
# ... 버전 변경, 버그 수정 커밋 ...
git switch master
git merge --no-ff release-1.4.0
git tag -a v1.4.0 -m "1.4.0"
git switch develop
git merge --no-ff release-1.4.0
git branch -d release-1.4.0
```

### 2020년의 회고

Driessen은 2020년 3월 원문 맨 위에 회고 노트(Note of reflection)를 붙였다. 요지는 다음과 같다.

- 이 모델은 10년도 더 전에 구상되었고, 이후 많은 팀이 일종의 표준이나 교조처럼 받아들였다.
- 지금 Git으로 만드는 소프트웨어의 다수는 지속적으로 전달되는 웹 앱이다. 지속적 전달을 하는 팀이라면 GitHub Flow 같은 더 단순한 워크플로를 권한다.
- 명시적으로 버전이 매겨지는 소프트웨어, 또는 여러 버전을 동시에 지원해야 하는 경우에는 여전히 잘 맞을 수 있다.
- 만능 해법은 없으니 자신의 맥락을 고려하라.

즉 Git Flow의 원저자 스스로 이 모델의 적용 범위를 "버전이 있는 릴리스"로 좁혔다.

### 작은 팀에서 드러나는 비용

- `develop`과 `master` 두 줄기를 맞춰야 한다. 핫픽스가 `develop`에 반영되지 않으면 다음 릴리스에서 버그가 되살아난다.
- 기능 브랜치가 `develop`으로 들어가고, 운영 반영은 릴리스 브랜치를 거쳐야 하므로 "코드 완료"에서 "사용자에게 도달"까지 단계가 하나 더 있다.
- GitHub에서 PR이 기본 브랜치가 아닌 `develop`을 대상으로 하면 `fixes #123` 같은 닫기 키워드가 동작하지 않는다. 닫기 키워드는 PR이 저장소의 기본 브랜치를 대상으로 할 때만 이슈를 연결하고 닫는다. `develop`을 기본 브랜치로 지정하면 해결되지만, 그러면 "기본 브랜치 = 운영 코드"라는 직관이 깨진다.

## GitHub Flow

GitHub 문서가 "가벼운 브랜치 기반 워크플로"로 소개하는 방식이다. 영구 브랜치는 기본 브랜치 하나이고, 단계는 여섯 개다.

1. 브랜치를 만든다.
2. 변경하고 커밋·푸시한다.
3. PR을 연다(초안 PR도 가능).
4. 리뷰 의견을 반영한다.
5. PR을 병합한다.
6. 브랜치를 삭제한다.

문서는 병합 후 브랜치를 지우라고 권하며, 삭제해도 PR과 커밋 이력은 남는다고 설명한다. 릴리스 브랜치나 `develop`이 없으므로 "기본 브랜치는 항상 배포 가능하다"는 전제가 성립해야 한다. 그 전제를 지키는 장치가 PR 리뷰와 CI다.

GitHub Flow는 브랜치의 **수명**을 규정하지 않는다. 같은 모델에서도 브랜치가 반나절 살 수도, 3주 살 수도 있다. 3주짜리 기능 브랜치는 이름만 GitHub Flow일 뿐 통합 비용은 Git Flow의 기능 브랜치와 같다.

## 트렁크 기반 개발

trunkbaseddevelopment.com은 이를 "개발자들이 트렁크(trunk)라는 단일 브랜치에서 협업하는 소스 관리 브랜칭 모델"로 정의하고, 다른 장기 개발 브랜치를 만들지 말라고 한다. 아주 작은 팀은 트렁크에 직접 커밋할 수 있고, 규모가 커지면 리뷰와 빌드 검증을 위해 **짧게 사는 기능 브랜치(Short-lived Feature Branch)**와 PR을 쓴다. 지속적 통합의 요구사항으로 모든 구성원이 적어도 24시간에 한 번은 트렁크에 커밋해야 한다고 본다.

DORA의 트렁크 기반 개발 역량 문서는 측정 가능한 기준을 준다.

| 요소 | 측정 | 목표 |
|---|---|---|
| 활성 브랜치 수 | 애플리케이션 저장소의 활성 브랜치 수 | 3개 이하 |
| 코드 프리즈 | 프리즈 횟수와 기간 | 없음 |
| 병합 빈도 | 매일 트렁크에 병합되는 브랜치 비율 | 하루 한 번 이상 |
| 리뷰 승인 시간 | 변경 승인까지 평균 시간, 특히 이상치 | 리뷰를 동기적으로, 개발의 일부로 |

같은 문서는 흔한 함정으로 여러 명의 승인을 요구하는 무거운 리뷰(개발자가 변경을 모아서 올리게 만든다)와, 리뷰를 기다리는 동안 다른 작업을 시작하는 비동기 리뷰(병합 충돌이 늘어난다)를 든다. CI가 깨지면 몇 분 안에 고치거나 되돌리라고 한다.

미완성 기능은 브랜치에 숨기는 대신 피처 플래그로 꺼 둔 채 트렁크에 넣는다. 이 부분은 [일감 크기 글](/2024/03/19/ticket-size-lead-time/)의 "배포와 릴리스를 분리한다"와 같은 원리다.

### 트렁크 기반에서의 릴리스 브랜치

트렁크 기반 개발도 릴리스 브랜치를 쓸 수 있다. 다만 Git Flow와 방향이 반대다.

- 릴리스 직전에 트렁크에서 필요한 시점(Just-in-time)에 자른다. 트렁크 개발은 멈추지 않는다.
- 릴리스 브랜치에서는 개발을 이어 가지 않는다.
- 버그는 **트렁크에서 먼저 재현·수정**하고 CI를 통과시킨 뒤, 그 커밋을 릴리스 브랜치로 체리픽(cherry-pick)한다. 릴리스 브랜치에서 고치고 나중에 병합하려 하면 누군가 잊어 운영 회귀가 생긴다는 이유다.
- 릴리스 브랜치는 트렁크로 다시 병합하지 않고, 해당 버전이 더 이상 운영되지 않으면 태그를 남기고 삭제한다.

```bash
# 트렁크에서 수정 후, 살아 있는 릴리스 브랜치로 체리픽
git switch main
git commit -m "fix: 녹음 업로드 재시도 시 중복 저장 방지"
git push origin main            # CI 통과 확인
git switch release/1.4
git cherry-pick -x <커밋 SHA>    # -x: 원본 커밋 SHA를 메시지에 남김
git tag -a v1.4.1 -m "1.4.1"
git push origin release/1.4 --tags
```

## 모바일 앱에서 릴리스 브랜치가 필요한 이유

백엔드는 트렁크에서 바로 배포하고, 문제가 생기면 다시 고쳐 배포하는 롤 포워드(Roll-forward)가 가능하다. 모바일 앱은 다르다.

- **심사 지연**: Apple은 평균적으로 제출의 90%가 24시간 안에 심사된다고 안내한다. Google Play는 일부 앱이 확장 심사를 받을 수 있고, 예외적으로 7일 이상 걸릴 수 있다고 안내한다. 수정 하나가 사용자에게 닿기까지 최소 하루가 걸린다.
- **구버전 공존**: 스토어에 올라간 빌드는 사용자가 업데이트할 때까지 계속 실행된다. 백엔드는 여러 앱 버전을 동시에 상대해야 한다.
- **긴급 심사**: Apple은 치명적 버그 수정 같은 사정이 있으면 심사 신속 처리(Expedited Review)를 요청할 수 있게 한다. 다만 요청 수단일 뿐 보장은 아니다.

심사가 진행되는 동안 트렁크에는 다음 기능이 계속 들어온다. 심사 중 반려되거나 출시 직후 치명적 버그가 발견되면, 그 사이 들어온 미완성 변경 없이 **심사받은 코드에 수정 하나만 얹어** 다시 제출해야 한다. 이때 필요한 것이 출시 시점에서 잘라 둔 릴리스 브랜치(또는 태그)다. 트렁크 기반 개발 사이트도 평소에는 트렁크 태그에서 릴리스하고, 운영 수정이 필요할 때만 그 태그에서 브랜치를 만드는 방식을 대안으로 든다.

```bash
# 평소: 트렁크의 특정 커밋에 태그를 달아 스토어 빌드
git tag -a app-v1.4.0 -m "store build 1.4.0+27"

# 출시 후 핫픽스가 필요할 때만 태그에서 브랜치 생성
git switch -c release/app-1.4 app-v1.4.0
```

## 병합 방식이 이력에 주는 영향

GitHub의 PR 병합 방식은 세 가지다.

| 방식 | 기본 브랜치 이력 | 장점 | 주의할 점 |
|---|---|---|---|
| 병합 커밋(Merge commit, `--no-ff`) | 브랜치의 모든 커밋 + 병합 커밋 | 브랜치 단위가 보존되고 통째로 되돌리기 쉽다 | 이력이 갈라져 읽기 어렵다. 선형 이력 강제 규칙과 함께 쓸 수 없다 |
| 스쿼시 병합(Squash and merge) | PR당 커밋 1개 | PR = 커밋이라 이력이 단순하다 | 개별 커밋의 작성자·날짜·SHA가 사라진다. 같은 브랜치로 작업을 이어 가면 이미 스쿼시된 커밋이 다시 나타나 충돌이 반복될 수 있다 |
| 리베이스 병합(Rebase and merge) | 브랜치 커밋을 하나씩 재적용, 병합 커밋 없음 | 선형 이력에 커밋 단위가 남는다 | GitHub는 항상 커미터 정보를 갱신하고 새 SHA를 만든다. GitHub가 대신 서명할 수 없어 서명 검증이 빠진다 |

스쿼시 병합의 "같은 브랜치로 이어 가면 충돌이 반복된다"는 성질은 짧게 사는 브랜치를 전제로 한다는 뜻이기도 하다. 병합 후 브랜치를 지우는 GitHub Flow, 트렁크 기반 개발과 잘 맞고, 장기 브랜치를 반복 병합하는 Git Flow의 `develop` → `master` 같은 경로에는 맞지 않는다. Git Flow는 원문대로 병합 커밋을 쓰는 편이 자연스럽다.

브랜치 보호(Branch Protection)는 전략을 강제하는 장치다. GitHub는 승인 리뷰 필수, 상태 체크 통과 필수, 선형 이력 강제, 강제 푸시·삭제 차단 같은 규칙을 기본 브랜치에 걸 수 있게 한다.

## 세 모델 비교

| 항목 | Git Flow | GitHub Flow | 트렁크 기반 개발 |
|---|---|---|---|
| 영구 브랜치 | `master`, `develop` | 기본 브랜치 1개 | 트렁크 1개 |
| 작업 브랜치 수명 | 규정 없음, 기능 단위라 길어지기 쉬움 | 규정 없음 | 짧게(DORA: 보통 몇 시간, 하루 한 번 이상 병합) |
| 미완성 기능 처리 | 기능 브랜치에 둔다 | 브랜치에 두거나 플래그 | 피처 플래그로 꺼 둔 채 트렁크에 |
| 릴리스 준비 | `develop`에서 `release-*` 분기 | 병합 = 배포 가능 | 필요할 때 트렁크에서 자르거나 태그에서 릴리스 |
| 핫픽스 | `master`에서 분기, 두 곳에 병합 | 일반 PR과 같음 | 트렁크에서 수정 후 릴리스 브랜치로 체리픽 |
| 잘 맞는 릴리스 모델 | 명시적 버전, 여러 버전 동시 지원 | 지속적 배포 웹·백엔드 | 지속적 배포, 높은 통합 빈도 |
| 전제 조건 | 릴리스 관리 담당 | 빠른 리뷰와 CI | 빠른 리뷰, 빠른 CI, 피처 플래그 |

## 작은 팀의 선택 기준

모델 이름보다 두 변수를 먼저 정한다. **배포 단위가 무엇인가**(언제든 배포 가능한 서버인가, 심사를 거치는 바이너리인가)와 **작업 브랜치를 얼마나 오래 살려 둘 것인가**다.

| 상황 | 권장 |
|---|---|
| 백엔드만, 2~5명 | 트렁크 기반(짧은 기능 브랜치 + PR). 스쿼시 병합, 병합 후 브랜치 삭제, 하루 한 번 이상 병합 |
| 모바일 앱, 2~5명 | 트렁크 기반 + 스토어 제출 커밋에 태그. 핫픽스가 필요할 때만 태그에서 릴리스 브랜치를 만들고 트렁크 수정을 체리픽 |
| 앱 + 백엔드를 같은 팀이 운영 | 저장소별로 다르게 둔다. 백엔드는 트렁크에서 배포, 앱은 태그·릴리스 브랜치. 백엔드 API는 구버전 앱을 고려해 하위 호환을 유지 |
| 여러 버전을 동시에 유지보수(설치형, 고객별 버전) | Git Flow 또는 버전별 릴리스 브랜치 |
| 리뷰가 하루 이상 밀리는 팀 | 전략을 바꾸기 전에 리뷰 대기부터 줄인다. 어떤 모델이든 브랜치 수명이 리뷰 대기만큼 늘어난다 |

인원 기준은 공식 수치가 아니라 경험칙이다. trunkbaseddevelopment.com도 직접 커밋과 짧은 브랜치 방식의 경계는 팀 규모와 커밋 빈도에 달려 있고 실무자 사이에 논쟁이 있다고 적는다.

## 정리

1. 브랜치 전략의 핵심 변수는 브랜치 종류가 아니라 작업 브랜치가 메인 줄기에서 떨어져 있는 기간이다. 통합을 미룰수록 의미 충돌과 리뷰 크기가 커진다.
2. Git Flow는 `develop`, `release-*`, `hotfix-*`로 버전 릴리스를 관리하는 모델이며, 원저자도 2020년 회고에서 지속적 전달 팀에는 더 단순한 방식을 권했다.
3. GitHub Flow는 기본 브랜치 하나와 PR로 단순하지만 브랜치 수명을 규정하지 않으므로, 수명 제한은 팀이 따로 정해야 한다.
4. 트렁크 기반 개발은 짧은 브랜치, 하루 한 번 이상 병합, 피처 플래그, 빠른 CI를 전제로 하며, 릴리스 브랜치는 트렁크에서 고친 것을 체리픽해 받는 용도로만 쓴다.
5. 모바일 앱은 심사 지연과 구버전 공존 때문에 출시 커밋의 태그와 필요 시 릴리스 브랜치가 필요하다. 백엔드는 트렁크에서 배포하고 하위 호환을 유지한다.
6. 병합 방식은 브랜치 수명과 맞춘다. 짧은 브랜치에는 스쿼시 병합, 장기 브랜치를 반복 병합하는 구조에는 병합 커밋이 맞는다.
